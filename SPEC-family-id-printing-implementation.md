## B. Final architecture

```
/admin/family-ids  (admin · supervisor · office)
        ↓
 search / filter / select families      OR      "Print by students…" → student picker
        └───────────────────┬───────────────────┘
                            ↓
                PrintSource (discriminated union)
                            ↓
        resolvePrintBatch(source, roster)          ← pure, no I/O, unit-tested
        drop LEFT → drop missing familyId → normalize → dedupe
                            ↓
                   unique familyIds[]
                            ↓
        get_family_cards(familyIds[])              ← SECURITY DEFINER, STABLE
        complete sibling roster + parentName + gate-consistent phone + className
                            ↓
        FamilyCardData[]  { familyId, students[{name, className→grade, transport}], parentName, parentPhone }
                            ↓
              ONE PDF renderer: FamilyCardsDocument
                            ↓
                    preview / download / print
```

**Invariants enforced by construction**
1. `FamilyCardsDocument` only ever accepts `FamilyCardData[]`; there is no student-keyed render path.
2. `resolvePrintBatch` is pure and returns IDs that already exist — it cannot allocate.
3. `get_family_cards` is `STABLE` → Postgres rejects writes inside it.
4. No module under `src/lib/print/**` or the print dialog may import a generation function (asserted by test).

## D. Family ID stability implementation

### D.0 Establish which overload is live (do this first, B3)

```sql
SELECT p.oid::regprocedure AS signature, pg_get_functiondef(p.oid) LIKE '%p_transport_filter%' AS has_filter
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname='public' AND p.proname='generate_family_ids';
```

Then, in the **same new migration** as D.1, remove ambiguity before redefining:

```sql
DROP FUNCTION IF EXISTS public.generate_family_ids();            -- stale 0-arg body
-- keep exactly one: generate_family_ids(p_transport_filter TEXT DEFAULT NULL)
```

### D.1 The invariant

> **One family key → one Family ID, for the lifetime of the key.**
> For any grouping key *k* (`'p:'||parentId`, else `'t:'||normalize_phone(parentPhone)`), every student resolving to *k* shares exactly one `familyId`; that value is allocated at most once and is never re-issued, re-numbered, or abandoned while a student of *k* remains enrolled.

Grouping semantics are **unchanged** — the audit found the rules themselves correct; only the allocation step is wrong.

### D.2 Fix B1 — reuse an existing family's ID

Inside the group loop, **before** allocating:

```sql
-- Does this family key already own an ID? (idempotency across time, not just per-run)
SELECT s."familyId" INTO v_existing
FROM public.students s
WHERE s."familyId" IS NOT NULL
  AND CASE
        WHEN v_group.family_key LIKE 'p:%'
          THEN s."parentId" IS NOT NULL AND 'p:' || s."parentId" = v_group.family_key
        ELSE public.normalize_phone(s."parentPhone") <> ''
             AND 't:' || public.normalize_phone(s."parentPhone") = v_group.family_key
      END
ORDER BY s."familyId"
LIMIT 1;

IF v_existing IS NOT NULL THEN
  v_family_id := v_existing;                       -- sibling joins the existing family
  v_joined    := v_joined + 1;
ELSE
  v_next_id   := v_next_id + 1;                    -- genuinely new family
  v_family_id := lpad(v_next_id::TEXT, 4, '0');
  v_created   := v_created + 1;
END IF;
```

Add `studentsJoined` to the returned JSON and to `GenerateSummary`, so the UI reports *"2 new families · 1 student joined an existing family."*

**Ordering note:** a student with a `parentId` whose siblings were grouped by phone (or vice-versa) resolves through whichever key they carry. Cross-key merges remain the admin's job via the existing `assign_family_override()` — unchanged behaviour, now surfaced by the mismatch flag in §F.

**Concurrency (cheap, do it here):** `PERFORM pg_advisory_xact_lock(hashtext('family_ids_generate'));` at the top — the function is being rewritten anyway.

### D.3 Fix B2 — stop destroying the ID

```sql
IF p_left THEN
  UPDATE public.students SET "transport" = 'LEFT' WHERE id = p_student_id;   -- keep familyId
ELSE
  UPDATE public.students SET "transport" = NULL   WHERE id = p_student_id;
END IF;
```

**Mandatory coupled change** — LEFT students now retain a `familyId`, so they must be excluded wherever a family is materialised, or a departed child reappears at the gate:

| Location | Change |
|---|---|
| `lookup_family()` (`20260802_fix_live_role_check.sql`) | add `AND COALESCE(s."transport",'') <> 'LEFT'` |
| `get_family_cards()` (new) | same predicate, built in from the start |
| `groupStudentsByFamily()` (`familyIds.ts:180`) | skip `transport === 'LEFT'` |
| `generate_family_ids()` | already excludes LEFT candidates — no change |

### D.4 Data repair for families already split

Report-only query shipped alongside the migration (admin runs it, then merges with the existing override UI — no new tooling):

```sql
SELECT COALESCE('p:'||s."parentId", 't:'||public.normalize_phone(s."parentPhone")) AS family_key,
       array_agg(DISTINCT s."familyId") AS ids, count(*) AS students
FROM public.students s
WHERE s."familyId" IS NOT NULL AND COALESCE(s."transport",'') <> 'LEFT'
  AND (s."parentId" IS NOT NULL OR public.normalize_phone(s."parentPhone") <> '')
GROUP BY 1 HAVING count(DISTINCT s."familyId") > 1;
```

## E. Grade on the card — data source and layout

### E.1 Authoritative field — **`students.className`**

Verified: there is **no** grade/year column on `students` in any of the 37 migrations. The table is `id, name, className, parentId, createdAt` plus the four family-ID columns. `className` (e.g. `Grade 7-A`, `KG-B`, `Foundation A`) is the authoritative value, drawn from the `CLASSES` constant (`src/types/index.ts:13`).

The instruction "do not infer grade from class names if a proper grade field exists" is satisfied: **none exists**, so `className` *is* the field.

**Terminology:** the school UI already labels this column **"Grade"** — `StudentDirectory.tsx:81`, the import mapper (`HEADER_ALIASES.grade`), and the gate's own string map (`gateStrings.ts`: `grade: 'Fasalka' / 'Grade'`). So we display the class value under the heading "Grade" and stay consistent.

⚠ **Do not reuse the name `getGrade`** — `src/types/index.ts:218` already exports `getGrade(score)` returning a **letter grade from an exam score**. New helper is `formatGradeLabel()`.

### E.2 The card already shows the class — the change is prominence

`KidRow` (`familyCards.tsx:210-222`) currently renders:

```
[badge]  Xalimo Xasan Maxamed          ← rowName 8.3pt bold
         Grade 7-A · WALKER            ← rowMeta 6.3pt, muted
```

So the grade is present but demoted and fused with transport. The requirement is grade **beside the name**.

### E.3 Measurement — the requested inline layout does not fit

I measured real glyph advances at the card's actual geometry.

Available `rowBody` width on a 60 mm pocket card: `60mm − 2×border − 2×3.5mm panel pad − 5.5mm badge − 2.3mm margin − 1mm pad = **123.3 pt**`.

| Name (8.3 pt bold) | Width | + `Grade 12-C` @6.8 | Fits 123.3? |
|---|---|---|---|
| Maxamed Aden | 60.9 | 100.6 | ✅ |
| Xalimo Xasan Maxamed | 94.1 | **133.8** | ❌ |
| Cabdiraxmaan Cali Yuusuf | 103.3 | **143.0** | ❌ |
| Cabdiraxmaan Maxamuud Warsame | 140.8 | **180.5** | ❌ (name alone already overflows) |

The repo's **own sample data** uses `Xalimo Xasan Maxamed` and `Cabdiraxmaan Cali Yuusuf` (`FamilyIds.tsx:44-70`), so overflow is the common case, not the edge case. Shortening to `G12` (12.9 pt) rescues the medium names but still fails the longest. `maxLines`/`textOverflow` were tested and **do not truncate** in `@react-pdf/renderer` 4.3.2 — the name simply wraps, silently pushing the grade out of alignment.

**Conclusion: reject the literal `Name — Grade` single line on the pocket/lanyard card.** It is not robust at this width with real Somali names.

### E.4 Specified layout — aligned secondary column (the doc's stated fallback)

Keep one row per student; give the grade its **own fixed-width right-aligned column**, so it can never wrap into or detach from a name:

```
[badge]  Xalimo Xasan Maxamed              G7      ← name flex:1, grade fixed 26pt right-aligned
         Bus 9                                      ← meta = transport only

[badge]  Cabdiraxmaan Cali Yuusuf          G12
         WALKER
```

Implementation in `KidRow`:

```tsx
<View style={styles.rowBody}>
  <View style={styles.nameLine}>                    {/* flexDirection: 'row', alignItems: 'baseline' */}
    <Text style={rowName}>{student.name}</Text>     {/* flex: 1, flexShrink: 1 — wraps if truly long */}
    <Text style={gradeChip}>{formatGradeLabel(student.className)}</Text>
  </View>                                            {/* width 26pt (38 large), textAlign right, flexShrink 0 */}
  <Text style={rowMeta}>{transportLabel(student.transport)}</Text>
</View>
```

* Grade is a **sibling of the name inside the same row `View`** → it is positionally bound to that student and cannot drift.
* `flexShrink: 0` on the chip + `flex: 1` on the name: a very long name wraps to a second line while the grade stays anchored top-right, still on that student's row.
* Removing `className` from the meta line frees the width the chip consumes — net layout cost ≈ zero.
* `placard` uses the existing `*Large` variants (chip 38 pt, 9.5 pt type).

**`formatGradeLabel(className)`** — new pure helper in `src/lib/transport.ts` (beside `transportLabel`/`displayFamilyId`), reusing the patterns already in `types/index.ts`:

| `className` | Chip | Rule |
|---|---|---|
| `Grade 7-A` | `G7` | `/^Grade (\d+)/` → `G$1` |
| `Grade 12-C` | `G12` | same |
| `KG-B` | `KG` | `/^KG/` → `KG` |
| `Foundation A` | `F-A` | `/^Foundation\s+([A-Z])/i` → `F-$1` |
| `Year 12-A` | `Y12` | `/^Year\s+(\d+)/i` → `Y$1` |
| anything else | first 3 chars, uppercased | never throws, never blank |
| `null`/`''` | `''` | renders nothing, row still valid |

Section stays `panelLabel = 'CHILDREN'`; the chip needs no header (it is self-evident and the gate lookup list already prints full class names).

**Vertical capacity re-verified with the change:** rendered 1/3/4/5/6/8 children; per-stream text-run census grows 31 → 36 → 41 for 4/5/6 kids and page objects stay at 2 — all rows are drawn, nothing clipped, front/back unaffected.

### E.5 Ordering and roster completeness — unchanged

`buildFamilyCardData` sorts students `a.name.localeCompare(b.name)` (`familyCards.tsx:404`) and families by `familyId`. **Preserved.** The grade travels inside each `Student` object, so student-selection printing still expands to the **full** roster and every unselected sibling gets their own grade (§B).

## G. Acceptance criteria

**Family ID stability**
1. Existing family + new sibling (same `parentId`) → sibling receives the **existing** ID; summary reports `studentsJoined: 1`, `familiesCreated: 0`.
2. Existing family + new sibling matched by `parentPhone` only → same result.
3. Brand-new family → new sequential ID; `familiesCreated: 1`.
4. Existing family re-import of the transport sheet → **zero** `familyId` values change.
5. Re-running Generate any number of times → zero changes; no duplicate IDs.
6. `mark_student_left(true)` → `transport='LEFT'`, **`familyId` unchanged**.
7. Restore → student rejoins their original family; no new ID.
8. LEFT student never appears in `lookup_family`, on a card, or in a family row.
9. Exactly one `generate_family_ids` overload exists; `rpc('generate_family_ids', {})` resolves unambiguously to the filtered body.
10. Two concurrent Generates cannot assign the same ID to different families.

**Printing**
11. Print one family → exactly 1 card, front + back, duplex-aligned.
12. Print N selected → exactly N cards; count shown on the button and in the dialog.
13. Print all → every family in the **current filter**, count stated.
14. Print by students: A(0042), B(0042), C(0071) → exactly **2** cards + "3 students → 2 cards · 1 duplicate merged".
15. Selecting multiple siblings of one family → 1 card.
16. Student with no `familyId` → listed as skipped, never silently dropped; no ID is generated.
17. Every card lists the **complete** current sibling roster, including unselected siblings.
18. Reprinting reuses the same `MBK-####` and performs no database write.
19. Search matches `42` / `0042` / `MBK-0042`, student name, parent name, phone.
20. Select-all-filtered and clear-selection behave exactly; selection keyed by `familyId`, survives filter/sort changes.

**Grade on card**
21. Every student row shows a grade chip derived from `className`; each sibling shows **their own** grade.
22. `formatGradeLabel`: `Grade 7-A→G7`, `Grade 12-C→G12`, `KG-B→KG`, `Foundation A→F-A`, `Year 12-A→Y12`, unknown→3-char fallback, null→`''` (no throw).
23. Grade never renders against the wrong student (chip is a child of that student's row).
24. Long name (`Cabdiraxmaan Maxamuud Warsame`) → grade stays anchored and legible; no overlap.
25. Family of 6 → all six rows with grades render inside the card; page objects remain 2.
26. Student ordering unchanged (alphabetical by name); family ordering unchanged (by `familyId`).
27. Placard layout renders the chip at the large size without regression.

**Permissions and data completeness**
28. Admin, supervisor and office printing the same family produce **identical** cards (same siblings, parent name, phone).
29. Supervisor with limited `assignedClasses` still gets the complete roster (via RPC).
30. Card phone == gate phone for the same family.
31. `get_family_cards` is `STABLE`, role-gated, PUBLIC execute revoked; parent/teacher denied.
32. `/admin/family-ids/setup` is admin-only, enforced by `canAccessRoute()`, the App switch, **and** SQL.

**Duplex / partial pages / regressions**
33. Regression test asserts measured back-page x-positions for 1–9 cards (fails if `justifyContent` changes).
34. 1 card and 3 cards (partial rows) remain correctly aligned.
35. Mixed-transport family shows all distinct modes; filter matches if **any** child matches.

**Separation and quality**
