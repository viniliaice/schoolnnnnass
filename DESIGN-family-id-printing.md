## 0. TL;DR — the recommendation in six lines

1. **Option C (hybrid)** — the Family IDs table is the printing home; one shared **Print batch dialog** is the confirmation step every print path funnels through. Not a separate Print Center page.
2. **Split the page into two tabs: `Families` (default, everyone) and `Import & Generate` (admin only).** Generation stops being step 1 of the workflow the office sees every day.
3. **Printing is family-based at the engine level, always.** "Print by students" is an *input mode* that resolves to a unique family set before anything is rendered.
4. **Add a `family_cards` print-log table + `record_family_card_print()` RPC.** That is what makes "card status", "reprint", and audit possible — and it never touches `students.familyId`.
5. **Fetch card data through a new `get_family_cards(TEXT[])` SECURITY DEFINER RPC.** Today the card contents depend on the caller's RLS visibility — a supervisor can print a card that is silently **missing a sibling** (§2.6). This is the most important defect found.
6. **Fix the duplex back-page mirroring for partial pages** before shipping "print one family" — today a single-card sheet prints its back on the wrong half (§2.5).

## 1. Current implementation and data flow

### 1.1 Data model — there is no `families` table

A "family" is a **derived grouping**, not a row. Everything lives on `students`
(`supabase/migrations/20260802_family_ids.sql:16-30`):

| Column | Type | Meaning |
|---|---|---|
| `govId` | TEXT | Sheet's `numberGov` |
| `transport` | TEXT | bus number (`'9'`), `'WALKER'`, `'CAR'`, `'LEFT'` (CHECK, `NOT VALID`) |
| `parentPhone` | TEXT | Sheet's `SECOND NUMBER`, normalized |
| `familyId` | TEXT | **4-digit zero-padded string** (`'0042'`) — indexed |

* `MBK-` is **display/print only** — `displayFamilyId()` in `src/lib/transport.ts:80`. Stored form is digits, gate input is digits (`gate-utils.ts`).
* Related tables: `release_log` (gate handoffs, `20260802_release_log.sql`), `audit_logs` (generic).
* **There is no card/print state anywhere.** `grep -i print supabase/` returns exactly one *comment*. No `printedAt`, no `printCount`, no batch table. The UI cannot tell "printed" from "never printed" today.

### 1.2 How families are identified

Inside `generate_family_ids()`:

```sql
CASE WHEN s."parentId" IS NOT NULL           THEN 'p:' || s."parentId"
     WHEN normalize_phone(s."parentPhone")<>'' THEN 't:' || normalize_phone(s."parentPhone")
     ELSE NULL END AS family_key
```

`parentId` first, else normalized phone; `NULL` key ⇒ **unattached** (surfaced in the amber bucket on the page, resolved with `assign_family_override()`). The key is used **only at generation time** — afterwards the family *is* the `familyId` string. Two siblings are "the same family" because they carry the same 4 digits, not because they point at a shared row.

### 1.3 How `MBK-####` numbers are generated

`generate_family_ids(p_transport_filter TEXT DEFAULT NULL)` — SECURITY DEFINER, **admin-only** in SQL, wrapped by `generateFamilyIds()` (`src/lib/db/familyIds.ts:37`).

* Next number: `MAX(normalize_family_id(familyId)::INTEGER) + 1`, `lpad(…,4,'0')`.
* Idempotent by construction: candidates are `WHERE "familyId" IS NULL`, and the write is `UPDATE … WHERE id = … AND "familyId" IS NULL`. **Re-running never reassigns an existing ID.**
* `LEFT` students are excluded (`20260802_mark_student_left.sql`).
* Optional transport filter (`bus` / `walker` / `empty` / `all`).
* Audit row `family_ids.generate` written in-function.

**⚠ Verify in production — possible overload ambiguity.** `generate_family_ids` is (re)defined in four migrations. In filename order the last two are `20260802_generate_transport_filter.sql` (creates the **1-arg, defaulted** version) and `20260802_mark_student_left.sql` (creates the **0-arg** version). If both were applied in that order, Postgres now holds *two overloads*, and a no-argument call — exactly what the client sends for "All" (`generateFamilyIds()` → `rpc('generate_family_ids', {})`) — is ambiguous (`PGRST203` / "function is not unique"). Filtered calls still resolve. Worth a one-line check (`\df generate_family_ids`) before any further work; if both exist, drop the 0-arg one in a new migration. Not caused by this change, but it sits directly under it.

### 1.4 How transport-sheet imports affect Family IDs

`src/lib/import/transportImport.ts` (XLSX/CSV/paste, header-name mapping, name-first matching with ambiguity flags) → `applyTransportImport()` (`familyIds.ts:113`) → per-row `set_student_import_fields()` RPC (admin-only) writing `govId`, `transport`, `parentPhone`.

**Import never writes `familyId`.** So today's answer to *"does re-importing change a family's ID?"* is: **no**, provided the import doesn't move a student between grouping keys. Two real ways an ID *can* drift, both worth naming:

* Import changes `parentPhone` for a student who is **still unassigned** → they may group differently on the next Generate. (Assigned students are immune — `WHERE familyId IS NULL`.)
* `mark_student_left(true)` **clears `familyId`**; restoring does not bring it back — the student gets a *new* family on the next Generate. That is a genuine "the ID moved" path and should be documented in the UI copy.

### 1.5 Current Family ID generation UI

`src/pages/admin/FamilyIds.tsx` — **936 lines, one component**, a linear 4-step wizard:

```
Help panel → stats row → progress bar (x of 200)
  1 · Generate family IDs        [admin only]
  2 · Import the transport sheet [admin only]
  3 · Families (read-only-ish table, transport quick-edit)
  4 · Print cards
+ Unattached bucket (assign / mark left)
+ Marked as left (restore)
```

The families table (line ~565) renders `Array.from(groupStudentsByFamily(students))`: columns **Family ID / Students / Transport / Phone**. No search, no filters, no sort, no pagination, **no row selection**, no per-row actions. It is a `max-h-96` scroll box. At the 200-family target that is unusable for "find MBK-0042".

### 1.6 Current print flow

`AsyncPrintLink` (`FamilyIds.tsx:767`) receives `filteredFamilies` — the *whole* family list narrowed only by a single `printFilter` select (`all | bus | walker | empty`, `FamilyIds.tsx:118-127`).

```
printFilter select
  → filteredFamilies : [familyId, Student[]][]
  → getParentNames(parentIds)        (profiles read)
  → buildFamilyCardData(...)         (familyCards.tsx:398)
  → pdf(<FamilyCardsDocument layout includeLookupList/>).toBlob()
  → preview in <iframe> (blob URL)  |  download via <a download>
```

Three layouts (`pocket` 60×90, `lanyard` 60×90, `placard` 148×105), QR drawn as a vector path (`qrPath.ts`), front+back pages for duplex lamination, optional gate lookup list page. A "Sample" button renders three hard-coded mock families.

**Is printing coupled to generation?** *Technically no* — no print path calls a write RPC; `pdf()` is pure client-side rendering. **Structurally yes**: it is "step 4" of a wizard whose step 1 is Generate, it is all-or-filtered only, and the only way to narrow the batch is a transport dropdown. There is no way to print one family, some families, or the families behind a set of students.

Additional defects in the current print path:

* The transport filter judges a family by `students[0].transport` only — a mixed family (walker + bus 9) lands in whichever bucket the alphabetically-first child happens to be in. Same bug on the printed badge (`familyCards.tsx:277`, already logged as finding 3.8 in `INVESTIGATION-family-ids.md`).
* Cards can only be produced for families that already have IDs (`groupStudentsByFamily` skips `familyId == null`) — correct, but the UI gives no signal about who was skipped.
* No batch size guard, no progress, no per-batch record of what was printed.

### 1.7 How students are associated with families

Only through the `familyId` string. No FK, no join table. Consequences that matter here:

* Student → family is `student.familyId` (nullable).
* Family → students is a client-side `groupStudentsByFamily()` over the full `getStudents()` result (`familyIds.ts:180`), or server-side `lookup_family(p_family_id)` for the gate.
* **Resolving a set of selected students to a set of families is a one-line `Set` operation** — the data shape already supports the requested feature; only the UI is missing.

## 2. Problems and limitations in the current printing workflow

| # | Severity | Problem |
|---|---|---|
| 2.1 | 🔴 High | **Only "print everything (optionally filtered by transport)" exists.** No one family, no selected families, no by-student. A lost card for MBK-0042 forces a 200-family PDF, then hunting page 11 in a viewer. |
| 2.2 | 🔴 High | **Card contents depend on the caller's RLS visibility.** `getStudents()` is a plain REST read. Admin and office have read-all policies; **supervisor does not** — supervisors only match "Teachers can read assigned class students" (`20260708_profiles_auth_session_rls.sql:60`). A supervisor printing MBK-0042 gets a card listing **only the children in their assigned classes** — a card missing a sibling is worse than no card at a safety gate. Same class of bug on `getParentNames()` (profiles are admin-read-only, so office/supervisor cards silently print an empty parent name). |
| 2.3 | 🟠 Medium | **No card/print state.** Nothing records that a card was ever printed, by whom, when, or how many times. "Reprint" is indistinguishable from "print", the office cannot answer "did family X ever receive a card?", and there is no audit for a physically distributed credential. |
| 2.4 | 🟠 Medium | **The families table doesn't scale to the workflow.** No search (by ID, student, parent), no bus/class filter, no sort, no selection, no pagination — a 200-row `max-h-96` scroller. |
| 2.5 | 🟠 Medium | **Duplex back-page mirroring breaks on partial pages.** `mirrorForLongEdge()` (`familyCards.tsx:335`) reverses each row *in place*: `[A]` → `[A]`, `[A,B,C]` → `[B,A,C]`. With 1 card, the front prints in the left column and the back also prints in the left column — after a long-edge flip the back lands on the **right**, i.e. on a blank half. Harmless today (batches are large and even); **a blocker the moment "print one family" ships**. Fix: pad each row to `cols` with empty slots before reversing. |
| 2.6 | 🟠 Medium | **Transport filter and printed transport badge read `students[0]` only** (`FamilyIds.tsx:124`, `familyCards.tsx:277`) — mixed-transport families are mis-filtered and mis-labelled. |
| 2.7 | 🟡 Low | **Generation is visually the front door.** Step 1 = Generate, and the office/supervisor see it disabled at the top of their daily screen. The mental model the user wants ("IDs are stable; printing is the routine act") is contradicted by the IA. |
| 2.8 | 🟡 Low | No batch-size guard/progress. 200 families ≈ 100 A4 pages rendered synchronously in the browser; the button just says "Preparing…". |
| 2.9 | 🟡 Low | No "how many cards will this print" count anywhere except an incidental `x of y families` hint next to the filter. |
| 2.10 | ⚪ Info | Nothing in the print path can create an ID today. That property is **correct and must be preserved by construction** (§7.4), not just by convention. |

## 3. Recommended UX — Option C (hybrid), and why

### The three options, judged against the dismissal-gate workflow

| | Option A — one page, filters + selection | Option B — dedicated Print Center | Option C — hybrid (table + print dialog) |
|---|---|---|---|
| Reprint one lost card | Search → row → Print. **Fast.** | Navigate → choose mode → search → select → batch. Slow for the 90% case. | Search → row → **Print card** (single-family dialog, 1 confirm). **Fastest.** |
| Print 10 selected families | Select rows → Print selected | Same, one page away | Select rows → Print selected → review dialog |
| Print by students | Awkward — a student picker inside a family table | Natural | Natural — it's a tab in the print dialog |
| Print all after import | Yes | Yes | Yes |
| Prevents duplicate cards | Nothing forces a review step | Batch screen shows the count | Dialog is *the* place the count + dedupe live |
| Places to maintain | 1 | 2 (table logic duplicated) | 1 table + 1 shared dialog |
| Places staff must learn | 1 | 2 | 1 (the dialog is a step, not a destination) |

**Recommendation: Option C.**

Why, specifically for a school dismissal gate:

1. **The dominant real-world job is a single reprint** — a lost or damaged card, one family at a time, requested at the office counter while a parent waits. That must be ~3 seconds from a search box, which argues for row-level actions (A), not a separate destination (B).
2. **The bulk job happens once or twice a year** (after the transport sheet import). It can afford one extra confirmation click, and it *should* have one: this is the batch that consumes 100 sheets of card stock and a laminator afternoon. A review step showing **"You are about to print 143 cards (143 families · 286 pages)"** is a feature, not friction.
3. **"Print by students" needs a different picker than the family table** (student search, class filter, per-student rows) and needs an explicit **dedupe disclosure** ("12 students → 7 cards"). Bolting that onto the family table (pure A) makes the table modal and confusing; giving it its own page (pure B) makes staff choose a destination before they know what they want. A tab inside the shared dialog is exactly the right size.
4. **One code path for rendering, one for confirming.** Every action — one family, selected families, all filtered, by students — resolves to the same `PrintBatch` and opens the same dialog. There is exactly one place where the count, the dedupe, the layout choice, the preview, and the print-log write live.

## 4. Recommended user flow (Family IDs page → paper)

**Flow 1 — reprint one lost card (the 90% case, target < 10 s)**
Open Families → type `0042` (or the child's name) → row matches → **Reprint** → dialog opens pre-scoped to that family, reason defaults to *Reprint — lost* → **Print 1 card** → PDF opens/downloads → print log records `reprint` → row Card column becomes "Reprinted 19/8 ×2". Same `MBK-0042`. No generation, no dialog gymnastics.

**Flow 2 — several families**
Filter (e.g. Bus 9) → tick 7 rows → **Print selected (7)** → dialog → Preview → Print. Selection survives filter changes and is shown as `7 selected (2 hidden by current filter)`.

**Flow 3 — by students**
**Print by students…** → student picker → search/select 10 students (or "select all in class G7A") → dialog shows `10 students → 6 cards (4 duplicates merged)` and lists any student with no Family ID as skipped → Print.

**Flow 4 — print all after import (start of year)**
Import & Generate tab → Import → Apply → Generate → success panel *"18 new family IDs. Print the 18 new cards →"* → dialog pre-filled with the new families only (not all 143). Alternative: Families tab → filter `Card status = Never printed` → **Print all filtered**.

**Flow 5 — a family that changed** (new sibling enrolled)
Generate assigns the new sibling into the existing family (shared `parentId`/phone) → the family's `studentsHash` no longer matches what was last printed → Card column shows **"Out of date"** → office prints a replacement card with the same `MBK-####`, reason *Data changed*.

## 5. Should printing be family-based, student-based, or both?

**Both as input, family-only as output — and that distinction should be explicit in the code.**

* The physical artifact is a **family card**. A card is meaningful only per `MBK-####`; there is no such thing as a student card in this system (the gate types a family ID, `lookup_family` returns the siblings).
* Student selection is how staff *think* when the request arrives class-by-class ("print cards for my new G7A intake"), so it must exist — as a **resolver**, not a second renderer.

Concretely: one function, one type.

```ts
// src/lib/print/printBatch.ts
export type PrintSource =
  | { kind: 'families'; familyIds: string[] }   // one family, selected rows, all filtered
  | { kind: 'students';  studentIds: string[] }; // by-students picker

export interface PrintBatch {
  families: FamilyPrintTarget[];   // deduped, sorted by familyId — what actually prints
  cardCount: number;               // = families.length, the number shown in the UI
  duplicatesMerged: number;        // students that collapsed into an already-included family
  skippedNoFamilyId: Student[];    // selected students with familyId == null
  skippedLeft: Student[];          // transport === 'LEFT'
}
export function resolvePrintBatch(source: PrintSource, all: Student[]): PrintBatch;
```

`PrintBatch` is the only thing `FamilyCardsDocument` ever sees. That makes "printing is family-based" a type-level fact, not a convention.

## 6. How student selection resolves to unique families

```
selected students
  → drop transport === 'LEFT'                      → skippedLeft
  → drop familyId == null / ''                     → skippedNoFamilyId
  → normalize: familyId.replace(/\D/g,'').padStart(4,'0')
  → dedupe into a Set<familyId>  (count collisions → duplicatesMerged)
  → for EACH familyId, expand to the FULL sibling roster from all students
      (never just the selected children — a card must always list the whole family)
  → sort by familyId ascending  (stable, matches the gate lookup list)
```

Worked example from the brief: A→0015, B→0015, C→0021 ⇒ `cardCount = 2`, `duplicatesMerged = 1`. If A has a third sibling D who was *not* selected, D **still appears on the MBK-0015 card** — that is the whole point of a family card, and it is why the resolver expands from the roster rather than from the selection.

Two UI consequences worth building deliberately:

* The dialog states the merge out loud (`"3 students → 2 cards · 1 duplicate family merged"`), so nobody thinks a card went missing.
* Students without a Family ID are shown, **not silently dropped**, with an admin-only shortcut *"Assign a family ID →"* that opens the existing override/generate path — clearly labelled as a separate, generating action.

## 7. Data / model considerations

### 7.1 Keep `familyId`-on-students; do not introduce a `families` table now

Tempting, but a `families` table means a migration of every existing ID, a new FK on `students`, and rewrites of `generate_family_ids`, `lookup_family`, `record_release`, the parent portal, and the gate. Printing does not need it. **Defer** (note it in `TODOS.md`); revisit only if the school ever wants per-family attributes (address, guardian list, pickup authorizations).

### 7.2 Add a print log — the one new table this feature needs

```sql
-- new migration, e.g. supabase/migrations/20260819_family_card_prints.sql
CREATE TABLE public.family_card_prints (
  id BIGSERIAL PRIMARY KEY,
  "familyId"   TEXT NOT NULL,            -- normalized 4-digit; no FK (no families table)
  "layout"     TEXT NOT NULL,            -- pocket | lanyard | placard
  "reason"     TEXT NOT NULL,            -- first | reprint_lost | reprint_damaged | data_changed | bulk
  "batchId"    UUID NOT NULL,            -- one batch = one PDF
  "studentIds" JSONB NOT NULL,           -- roster snapshot at print time (drives "out of date")
  "printedBy"  TEXT NOT NULL REFERENCES public.profiles(id),
  "createdAt"  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON public.family_card_prints ("familyId", "createdAt" DESC);
CREATE INDEX ON public.family_card_prints ("batchId");
```

* RLS: SELECT for `admin|supervisor|office`; **no INSERT/UPDATE/DELETE policies** — writes only via `record_family_card_print()` (the `release_log` pattern, `20260802_release_log.sql`).
* Card status per family is then a cheap aggregate: `Never printed` / `Printed <date>` / `Reprinted ×N` / `Out of date` (roster snapshot ≠ current roster).
* **Do not** derive print status from `audit_logs`: it is world-readable *and* world-insertable for any authenticated user (`00001_create_audit_logs.sql:13,18`; finding 3.2 in `INVESTIGATION-family-ids.md`) — a parent could forge print history. Mirror the event into `audit_logs` for the trail, but keep `family_card_prints` authoritative.

### 7.3 Read card data through an RPC, not through RLS-scoped REST

```sql
CREATE FUNCTION public.get_family_cards(p_family_ids TEXT[])
RETURNS JSONB  -- [{familyId, students:[{id,name,className,transport}], parentName, parentPhone, lastPrintedAt, printCount}]
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public
```

Gated to `admin|supervisor|office` (same role set as `lookup_family` after `20260802_office_role.sql`). This fixes §2.2 and §2.3 in one move: **a printed card is complete and identical no matter who printed it**, and the parent name stops depending on the admin-only `profiles` read. Model it directly on `lookup_family()` — including the `COALESCE(profile.phone1, phone2, students.parentPhone)` phone resolution, which the current print path doesn't do (cards print the sheet phone even when a better profile phone exists).

### 7.4 Structural guarantee: printing cannot generate

* No print module may import `generateFamilyIds` / `assignFamilyOverride` / `set_student_transport`. Enforce with a unit test in the style of the existing regression test *"writes via RPC, never a direct UPDATE"* (`family-ids.test.ts:93`): assert that running every print path calls **only** `get_family_cards` and `record_family_card_print`.
* The print dialog renders `familyId` values it received; it never computes one. `resolvePrintBatch` has no write access by type.

### 7.5 Idempotency of the ID itself (already true — keep it that way)

Re-import → `set_student_import_fields` (never touches `familyId`). Re-generate → `WHERE familyId IS NULL`. The two drift paths in §1.4 (unassigned student changing phone; `mark_student_left` clearing the ID) should be surfaced as UI copy on the Generate panel and the Mark-as-left button, not "fixed" silently.

## 8. Edge cases

| Case | Behaviour |
|---|---|
| Family with 1 student | Normal card. Duplex padding fix (§2.5) matters most here. |
| Family with many students (5+) | Card layout must clamp: show N rows, then "+3 more"; or auto-switch to placard. Decide a max (**recommend 6 rows**) and test it — today the rows just overflow the 90 mm card. |
| Student with no `familyId` | Never silently dropped: listed in the dialog as *skipped*, with an admin-only "Assign a family ID →" escape hatch. |
| Student marked `LEFT` | Excluded from resolution **and** from the printed roster. If a family becomes all-LEFT, its row shows *Inactive* and is excluded from "Print all filtered" by default (a `Show inactive` toggle can reveal it). |
| Selected students span the same family | Merged; count disclosed. |
| Family roster changed since last print | `studentIds` snapshot ≠ current roster ⇒ Card status **Out of date**; a filter chip lets the office print exactly those. |
| Two families sharing one phone (grouping error) | Pre-existing data problem, surfaced by the table (a "family" with implausibly many students). Resolution stays in the admin override flow — **not** in the print dialog. |
| Duplicate/oversized manual ID | Already guarded: `assignFamilyOverride` caps at 4 digits client-side and in SQL. |
| Print all with 0 families | Buttons disabled + empty state pointing at Import & Generate (admin) or "ask an admin" (office/supervisor). |
| Very large batch (>150 cards) | Warn ("≈ 76 sheets, this may take a minute"), render with progress, offer chunking into 50-family PDFs. |
| PDF render failure | Current code shows a flat "Could not build the PDF"; add the failing family ID to the message and keep the batch selectable for retry. |
| Concurrent Generate by two admins | Pre-existing race (finding 3.6 — no advisory lock). Unrelated to printing, but a duplicate ID would produce two cards with the same number: worth fixing with `pg_advisory_xact_lock` in the same release. |
| Office/supervisor tries to generate | Button not rendered; SQL rejects anyway. |
| Offline/slow gate network | Printing is an office-desk activity, not a gate activity — no offline requirement. The gate lookup list page stays as the paper fallback. |

## 9. Permission and security considerations

| Action | admin | supervisor | office | teacher | parent |
|---|---|---|---|---|---|
| Open `/admin/family-ids` | ✅ | ✅ | ✅ | ❌ | ❌ |
| View family table / search / filter | ✅ | ✅ | ✅ | ❌ | ❌ |
| **Print / reprint cards** | ✅ | ✅ | ✅ | ❌ | ❌ (own family only, portal) |
| Generate IDs | ✅ | ❌ | ❌ | ❌ | ❌ |
| Import transport sheet | ✅ | ❌ | ❌ | ❌ | ❌ |
| Override / mark left / edit transport | ✅ | ❌ | ❌ | ❌ | ❌ |
| Read print log | ✅ | ✅ | ✅ | ❌ | ❌ |

* Add `canPrintFamilyCards(role)` to `src/lib/routing.ts` next to `canGenerateFamilyIds()` — single source of truth, already mirrored by a role×route test (`routing.test.ts`).
* **UI guards are not security**: `get_family_cards` and `record_family_card_print` must role-check in SQL (`current_profile_role()`), `REVOKE … FROM PUBLIC`, `GRANT EXECUTE … TO authenticated` — the established pattern in every family-ID migration.
* A family card is a **physical credential for collecting a child**. Treat printing as an auditable act: every batch writes `family_card_prints` + an `audit_logs` mirror (`family_ids.card_print`) with who/when/why/how many. That is also the answer to "a card was found in the street" — you can see who printed it.
* Cards carry children's names, classes and a parent phone. Keep the PDF **client-generated and never uploaded**; blob URLs must be revoked after use (the current code does this — preserve it).
* Parent portal reprint stays scoped to the parent's own family (`getParentFamilyCard`, RLS-enforced). If the portal reprint is ever wired to the print log, it must record `printedBy = the parent` and must not be able to write another family's row.
* Do **not** widen `audit_logs` reliance; consider tightening its policies in the same release (finding 3.2).

## 12. Acceptance criteria

**Separation of concerns**
1. No print action anywhere in the app issues a new `MBK-####`. A unit test asserts the print paths call only `get_family_cards` / `record_family_card_print`, and never `generate_family_ids`, `assign_family_override`, or `set_student_transport`.
2. Reprinting MBK-0042 twice produces byte-identical family identity (same `familyId`, same students) and two rows in `family_card_prints`.
3. Re-running Generate after any number of prints changes zero existing `familyId` values (existing idempotency test extended with a print step in between).
4. Re-importing the transport sheet for already-assigned students leaves every `familyId` unchanged.

**Printing — the five actions**
5. **Print one family**: a row's `Print`/`Reprint` produces a PDF with exactly 1 card (front + back), correctly duplex-aligned on a partial sheet.
6. **Print selected**: N selected rows produce exactly N cards; the button label and the dialog both show N before printing.
7. **Print all**: prints every family matching the *current filters*, and the button states the count explicitly ("Print all filtered (143)").
8. **Print by students**: selecting students A(0015), B(0015), C(0021) produces exactly **2** cards, and the dialog states "3 students → 2 cards · 1 duplicate family merged".
9. **Reprint**: reuses the existing `MBK-####`, records `reason = reprint_*`, and updates the row's Card column to "Reprinted <date> ×N".
10. Every printed card lists **all** current siblings in the family, including students the user did not select.

**Table / selection / search**
11. Search matches Family ID (`0042`, `42`, `MBK-0042`), student name, parent name, and parent phone.
12. Filters exist for bus/route, transport mode, class/grade, and card status (Never printed / Printed / Out of date), and combine.
13. "Select all filtered" selects exactly the filtered rows; "Clear selection" empties it; selection is keyed by `familyId` and survives filter/sort changes, with hidden-selection count disclosed.
14. The table is usable at 200+ families: search-to-row in < 3 s, no full-list scroll hunting, and it renders at 375 px width.

**Correctness / safety**
15. A supervisor and an admin printing the same family get **identical** card content (all siblings, same parent name and phone) — verified against the RLS test suite.
16. Selected students with no `familyId` are listed as skipped, never silently dropped; LEFT students never appear on a card.
17. Preview renders the exact PDF that will be printed (same blob), and blob URLs are revoked on close.
18. Batches over the warn threshold show a size warning and a progress indication; a render failure names the family that failed and leaves the selection intact.

**Permissions / audit**
19. Office and supervisor can print but cannot see or invoke Generate / Import / override — enforced in UI *and* rejected in SQL.
20. Teacher and parent cannot reach `/admin/family-ids`; a parent can still print only their own family from the portal.
21. Every print batch writes `family_card_prints` (familyId, layout, reason, batchId, roster snapshot, printedBy, timestamp) and mirrors one `audit_logs` entry; `family_card_prints` has no direct INSERT/UPDATE/DELETE policy.

**Quality gates**
22. `npm run typecheck` clean; `npm run test:ci` green except the 3 known pre-existing `lesson-plan-decisions.test.ts` failures; `vite build` succeeds.
23. New tests cover: `resolvePrintBatch` (dedupe / roster expansion / skips / ordering), duplex mirroring with 1–4 cards, the print RPC wrappers, the print-never-generates regression, and a role×action matrix.

## Open questions for the user

1. **Card status source of truth** — do you want the `family_card_prints` log (adds a migration, enables "Never printed" / "Out of date" filters and audit), or is a purely stateless print flow acceptable for now? The log is what makes items 9, 12 and 21 possible.

5. **Batch chunking threshold** — one 143-card PDF, or auto-split into 50-family files for the office printer?
6. **Placement** — keep everything under `/admin/family-ids` (recommended), or expose a separate `/family-cards` entry in the office sidebar pointing at the same page with the Families tab preselected?
