## Final Verdict
# GO WITH CONDITIONS

The core bulk-upload change is **production-credible for the critical path**:
- right student
- right subject
- right assessment
- right score
- right authorization
- right database result

However, I am **not** comfortable issuing an unconditional `GO` because two material conditions remain:

1. **Deleted expected grade columns are silently accepted.**  
   Removing a known assessment column (reproduced with `ENGLISH CPW3`) does not mis-wire later columns, but it also does not raise a parser or server error. That is an integrity/UX gap, especially because the Instructions sheet currently says tampering is detected and rejected.

2. **Downstream monthly/final report decimal behavior is not independently verifiable from the repository state.**  
   The client calls `get_monthly_report` and `get_final_report`, but no corresponding repo-shipped migrations were found, so end-to-end decimal preservation for those report paths must be treated as `NOT VERIFIED`.

## AUDIT FINDINGS

### AUDIT FINDING A1 — Missing expected grade columns are not explicitly detected
**Severity:** Medium  
**Status:** Reproduced in execution

**Reproduction:**
- Fresh workbook generated.
- Populated later English columns (`CPW4`, `Attendance`, `MT`, `Akhlaaq`).
- Physically removed the `ENGLISH CPW3` column from the workbook.
- Parsed result returned `issues: []`.
- Later values still mapped correctly to their own headers, so there was no cross-wire.

**Why this matters:**
- Silent omission is safer than mis-routing, but it can still hide accidental loss of an assessment column.
- The current Instructions text says tampering is detected and rejected, which is not true for deleted expected columns.

**Static cause:**
- `parseRosterWorkbook()` validates only the headers that are present and recognized; it does not compare the uploaded header set against the expected selected subject/block contract. See `src/lib/bulk-grades/workbook.ts:394-429`.

### AUDIT FINDING A2 — Monthly/final report decimal preservation is not independently provable from repo-shipped server artifacts
**Severity:** Medium  
**Status:** Verification gap / repo drift risk

**Evidence:**
- `src/lib/db/reports.ts` calls RPCs `get_monthly_report` and `get_final_report`.
- Repository search found no corresponding `supabase/migrations/*` definitions for those RPCs.
- Therefore, monthly/final downstream decimal handling must remain `NOT VERIFIED` in this audit.
