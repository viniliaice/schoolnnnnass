# PLAN: Async "Submit to Supervisor" (Lesson Plans)

Generated by /investigate + /plan-design-review on 2026-08-13
Branch: arena/019ff7ff-schoolnnnnass
Repo: viniliaice/schoolnnnnass
Status: APPROVED

## Problem Statement

"Submit to Supervisor" is slow for teachers. The submit button awaits the entire AI
review pipeline synchronously before confirming the submission. Root cause (confirmed
by /investigate):

1. `submitForReview()` (`src/lib/db/lessonPlans.ts`) calls
   `supabase.functions.invoke('generate-lesson-review')` **synchronously** and blocks
   the teacher on the LLM result (NVIDIA primary, 70s abort × 2 attempts, Zen fallback).
2. After the edge function returns, it **synchronously** awaits
   `regeneratePeriodAiReviews()` (per-period review rows) and then
   `generateLessonPlanQuizzes()` — a second AI edge function with bounded retries +
   backoff. Only after ALL THREE complete does the teacher get the success toast and
   leave the "Submitting…" overlay.
3. A hung/stalled provider request therefore hangs the **teacher's submit button** —
   matching the previously-flagged "AI review sometimes hangs (107+ min waiting)" symptom.

The AI review is for the supervisor, not the teacher. Submitting is just a status change
and must be instant.

## Confirmed Sequencing Facts (investigation)

- **No dependency on 'submitted' first.** The `generate-lesson-review` edge function
  accepts any status except `in_review`/`approved` (409) and flips the plan to
  `in_review` (success) or `ai_failed` (failure) itself. The current happy path
  (`draft` → `in_review`) never uses `submitted` at all.
- **'submitted' is already a first-class "pending AI" state**: supervisor list query
  includes it (`fetchPlansBySupervisor`), the filter dropdown has "Submitted (pending AI)",
  the detail pane has the `waitingOnAi` blue spinner chip ("AI review still running") and
  the `aiLikelyStuck` orange banner, the `useAiReviewTimeout` watchdog and the
  `expire_stuck_ai_reviews` RPC flip `submitted` → `ai_failed` after 3 minutes.
- **Server-side teacher lock** (`enforce_lesson_plan_lock` trigger) is status-driven:
  setting `status='submitted'` immediately locks teacher edits to plan content and
  periods, while pure status/metadata changes remain allowed. This is exactly the
  existing "teacher-edit lock" requirement.
- **Race found:** the edge function's status writes are unconditional
  (`UPDATE … WHERE id = …`). With a background review, a supervisor could approve while
  the review is mid-flight; the edge's later flip would clobber `approved`/`rejected`.
  Fix: guard both status writes with `status IN ('submitted','ai_failed')`.

## Design

### Flow after fix

```
teacher clicks "Submit to Supervisor"
  → savePeriods (fast, awaited — content must be persisted before locking)
  → submitForReview: stamp ai_started_at, UPDATE lesson_plans SET status='submitted'
      → returns immediately  [teacher sees success toast; plan locked; supervisor sees it]
  → fire-and-forget background chain (not awaited, never throws to the UI):
      runAiReviewInBackground(planId, periods, unitContext)
        ├─ invoke generate-lesson-review   (edge persists ai_reviews row; flips
        │    submitted→in_review on success, →ai_failed on failure; both guarded)
        ├─ regeneratePeriodAiReviews()     (per-period rows in lesson_period_ai_reviews)
        └─ generateLessonPlanQuizzes()     (auto quizzes; failures logged, retryable
                                             from supervisor screen)
supervisor screen
  → plan appears as "Submitted (pending AI)" with blue "AI review still running" chip
  → review lands → chip clears; AI review panel renders (realtime ai_reviews channel)
  → >3 min with no review → watchdog flips to ai_failed → orange banner + Retry AI
    review button (existing behavior) — the supervisor is never blocked either way
```

### Design decisions (made by the review, each mapped to a principle)

| # | Decision | Why (principle) |
|---|----------|-----------------|
| D1 | Status write first (`submitted`), then background AI. | Sequencing correctness: edge accepts any non-in_review/approved status; supervisor "pending" state, watchdog, and lock all key off `submitted`. |
| D2 | Background chain is browser-side fire-and-forget (`void` chain inside the mutation), not a queue/infra change. | User spec: "background/fire-and-forget call". Existing `expire_stuck_ai_reviews` watchdog + supervisor retry already cover a lost background call (plan → ai_failed → retryable). No pg_net/pg_cron infra exists in this repo; adding it is out of scope. |
| D3 | Edge function status writes become conditional: `UPDATE … SET status='in_review' WHERE id=… AND status IN ('submitted','ai_failed')` (same for `ai_failed`). | Race safety (user spec: "status/FK ordering"). Supervisor decisions are authoritative; a background flip must never clobber `approved`/`rejected`. |
| D4 | `submitForReview` returns a fast result `{ plan_id, status: 'submitted' }`; no longer throws `SubmissionAiError` (removed — nothing awaits the AI anymore in the submit path). | Interaction-state honesty: success means "submitted", not "AI done". |
| D5 | `SubmissionAiError` class removed; `handleSubmit`'s `aiFailedOnly` branch deleted. | Dead code after the fix (nothing in the submit path can fail from AI anymore). Supervisor retry already handles ai_failed with its own error surface. |
| D6 | Supervisor pending UI = existing `waitingOnAi` chip + `aiLikelyStuck` banner (no new UI invented). Copy tightened: chip says "AI review still running", banner unchanged. | Subtraction default / reuse existing vocabulary (`STATUS_META` chips, blue/amber semantics). |
| D7 | Teacher success toast copy updated: "Submitted to supervisor — AI review runs in the background." | Honest mental model: teacher's job is done; the review is not their wait. |

### Interaction state table (Pass 2)

```
FEATURE                    | LOADING            | EMPTY            | ERROR                    | SUCCESS                  | PARTIAL
---------------------------|-------------------|-----------------|--------------------------|--------------------------|-----------------------
Teacher submit button      | "Submitting…"     | n/a (needs topic) | toast "Submission failed — plan not sent" | toast "Submitted to supervisor — AI review runs in the background" | n/a
Teacher submitted list     | existing spinner  | "No plans"      | n/a                      | "Submitted" blue chip    | n/a
Supervisor pending review  | n/a               | n/a             | banner + reason + Retry  | review panel renders     | chip "AI review still running" until review lands
Supervisor retry           | Retry button spinner | n/a         | retryError text under button | toast "AI review and quizzes generated" | generate-now/regenerate buttons for period reviews + quizzes
```

### What already exists (reused, not rebuilt)

- `waitingOnAi` chip + `aiLikelyStuck` banner + retry flow in `src/pages/supervisor/LessonPlanReview.tsx`
- `useAiReviewTimeout` watchdog + `expire_stuck_ai_reviews` RPC + `ai_review_logs` auditing
- Realtime channels: `lesson_plans` (usePlanWithPeriods), `ai_reviews` (useReview), `lesson_period_ai_reviews` (usePeriodAiReviews)
- `ai_reviews`, `lesson_period_ai_reviews`, `ai_review_logs` tables; `regeneratePeriodAiReviews` + `generateLessonPlanQuizzes` helpers
- `SubmissionAiError` → removed (superseded by the async design)

### NOT in scope

- Server-side queue/pg_net for background work (deferred — watchdog makes it recoverable)
- Changing supervisor retry to async (opt-in action; supervisor expects to wait)
- Moving `regeneratePeriodAiReviews`/quiz generation earlier or making them conditional on review success (they are cheap/local or independently retryable)
