# Design: Unit Plans

Generated by /office-hours on 2026-07-27
Branch: unknown
Repo: MBK International School
Status: DRAFT
Mode: Startup

## Problem Statement

Teachers at MBK International School create weekly lesson plans that go through AI review and supervisor audit. There is no curriculum-level grouping — lesson plans exist week-by-week without a parent unit to tie them together. The AI review prompt already references "unit plan" conceptually, but no unit structure exists in the data model.

## Demand Evidence

The school already uses the system with real teachers and a supervisor who audits lesson plans via AI. The supervisor needs a coherent view of how individual lessons build toward broader curriculum objectives. Without units, each lesson is reviewed in isolation — the supervisor can't evaluate whether the sequence of lessons covers a complete topic.

## Status Quo

Teachers use spreadsheets and paper to plan their curriculum sequence. Lesson plans are created week-by-week in the app, but there's no connection between them beyond the teacher's external notes. The supervisor sees individual lesson plans without understanding the larger topic structure.

## Target User & Narrowest Wedge

**Target users:** Teachers (create unit plans) and Supervisors (review lessons in unit context).

**Narrowest wedge:** A unit has a name, subject, class, date range (start/end week), and learning objectives. Lesson plans reference a `unitId`. That's it — no student data, no auto-generation, no complex curriculum mapping.

## Constraints

- Non-profit school — resources are limited, keep it simple
- Existing `lesson_plans` and `lesson_plan_periods` tables must not be restructured
- Must work within the existing role system (teacher, supervisor, admin)
- Must integrate with the existing AI review flow so supervisors see lessons in unit context

## Premises

1. A unit is a grouping layer — a unit has a name, subject, class, date range, and objectives. Lesson plans reference a `unitId`.
2. Units are created by teachers (or admin) — not auto-generated.
3. Supervisors review lessons within a unit context — the unit's objectives become the benchmark for AI review of each lesson plan.
4. No student-level data on a unit — it's a curriculum planning structure, not a tracking one.

## Approaches Considered

### Approach A: Minimal Viable (RECOMMENDED)
- New `unit_plans` table with core fields
- Add `unit_id` FK to `lesson_plans`
- Simple create/edit page for teachers
- Effort: S | Risk: Low

### Approach B: Ideal Architecture
- Same table + FK as A, with richer fields and AI-assisted objective generation
- Full CRUD UI with filtering
- Unit context flows into AI review prompt
- Effort: M | Risk: Low

### Approach C: Implicit Unit
- Add unit columns directly to `lesson_plans` instead of a new table
- Lesson plans with matching `unit_name` form an implicit unit
- Effort: XS | Risk: Low — but loses referential integrity

## Recommended Approach

**Approach A: Minimal Viable.** A dedicated `unit_plans` table with an FK relationship to `lesson_plans` is the right abstraction boundary. It's minimal but correct — you can enrich it later without changing the schema shape.

## Data Model

### New table: `unit_plans`

```sql
CREATE TABLE public.unit_plans (
  id text NOT NULL,  -- generated via newId('unit') in app layer, matching existing pattern
  name text NOT NULL,
  subject_id text NOT NULL REFERENCES public.subjects(id),
  class_name text NOT NULL,
  term_id text NOT NULL REFERENCES public.terms(id),
  week_number_start integer NOT NULL CHECK (week_number_start >= 1),
  week_number_end integer NOT NULL CHECK (week_number_end >= week_number_start),
  objectives text NOT NULL,
  teacher_id text NOT NULL REFERENCES public.profiles(id),
  created_at timestamp with time zone NOT NULL DEFAULT now(),
  updated_at timestamp with time zone NOT NULL DEFAULT now(),
  CONSTRAINT unit_plans_pkey PRIMARY KEY (id)
);
```

Uses `term_id` + `week_number` (1-indexed within a term) instead of freeform text. The existing `lesson_plans.week_label` format like "Week 1" is display-only; this stores the structural reference. The term defines the academic period and the week numbers are sequential within it.

### Modification to `lesson_plans`

Add column: `unit_id text REFERENCES public.unit_plans(id) ON DELETE SET NULL` (nullable — existing lesson plans have no unit; setting unit to null on delete rather than blocking deletes)

### Indexes
- `CREATE INDEX idx_unit_plans_teacher ON unit_plans(teacher_id);`
- `CREATE INDEX idx_unit_plans_term ON unit_plans(term_id);`
- `CREATE INDEX idx_unit_plans_class_subject ON unit_plans(class_name, subject_id);`
- `CREATE INDEX idx_lesson_plans_unit ON lesson_plans(unit_id);`

### Type note

`unit_plans.id` and `lesson_plans.unit_id` are both `text`, matching the existing pattern (`lesson_plans.id` is `text`, `profiles.id` is `text`, etc.). IDs are generated via the `newId('prefix')` helper (`prefix-timestamp-random`), **not** `gen_random_uuid()` — every existing table uses the `newId()` pattern and this must stay consistent.

`class_name` is `text` — same as `lesson_plans.class_name` and `attendance.className`; the app uses className strings, not FK references to a separate `classes` table.

Lesson count on the list view is computed via a simple `COUNT(*)` query on `lesson_plans WHERE unit_id = $id` (can be a subquery or separate aggregation).

### Row-Level Security

Policies mirror the existing `lesson_plans` pattern:

- **Teachers:** can INSERT, SELECT, UPDATE, DELETE their own units (`teacher_id = auth.uid()`)
- **Supervisors:** SELECT only — all units (to review lesson plans in context)
- **Admin:** full CRUD on all units

## UI Flow

**Sidebar:** Add "Unit Plans" nav item under teaching section for teachers, admin, and supervisor roles. Teachers see only their own units; supervisors see all units (read-only, no create/edit); admin sees all units with full CRUD.

**Unit Plans Page (`/teacher/unit-plans`):**
- List view: all units for the teacher's classes, sorted by start_week
- Each row: name, subject, class, date range, lesson count
- Create button opens a form

**Create/Edit Unit Form:**
- Name (required)
- Subject dropdown (from `class_subjects` join where teacher is assigned; admin sees all)
- Class dropdown (from teacher's `profiles.assignedClasses` JSONB; admin sees all classes)
- Term dropdown (from `terms` — filtered to current + upcoming)
- Start week, End week (number inputs 1-N, validated against term's week count)
- Objectives (textarea)

**States:**
- **Empty:** "No unit plans yet. Create your first unit to start grouping your lesson plans." plus Create button.
- **Loading:** Skeleton rows matching the list layout.
- **Error:** Toast on save failure; inline error on field validation.

**Lesson Plan integration:**
- On the create/edit lesson plan page, add a "Unit" dropdown showing available units for that subject + class (filtered by term_id, ordered by week_number_start)
- Selected unit's `objectives` field is stored in the AI review context (passed to the review Edge Function as additional context)

**AI Review integration:**
- When a lesson plan has a `unit_id`, the AI review function (`supabase/functions/generate-lesson-review/index.ts`) receives the unit's `name` and `objectives` as additional context parameters
- The system prompt appends: "This lesson is part of the unit '{unit_name}' with the following objectives: {unit_objectives}. Evaluate how well this lesson serves those unit objectives."
- The AI review results page displays the unit name above the lesson plan title
- No schema changes to `ai_reviews` — unit context is passed via the existing API parameters

## Distribution Plan

New files added to the existing React + Vite project. No external distribution needed — this is an in-app feature shipping with the next build.

## Edge Cases

- **Deleting a unit with lesson plans** — `ON DELETE SET NULL` handles the DB, but the lesson plan UI must gracefully show "(No unit)"
- **Overlapping week ranges** — validate `week_number_end >= week_number_start` in both UI and DB layer
- **Cross-term units** — a unit should live within one term; validate `week_number_start` and `end` don't span term boundaries
- **Teacher changes classes** — unit plans for old classes remain visible (read-only)
- **Existing lesson plans with no unit** — `unit_id` is nullable, UI shows "(No unit)" as default
