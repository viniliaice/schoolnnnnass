# Bulk Upload Grades Audit

**Repository:** `viniliaice/schoolnnnnass`  
**Branch audited:** `arena/01a076de-schoolnnnnass`  
**Audit date:** 2026-09-06  
**Scope:** Teacher/admin Excel bulk grade upload, its parser, client data flow, Supabase RPC/RLS/schema, and the multi-class/multi-subject teaching scenario.

> **Evidence standard:** Findings below are based on the checked-in source, migrations, tests, documentation, and the committed workbook. No live Supabase project, production data, credentials, or database connection was available in the checkout. Statements about live deployment state are therefore called out as verification items rather than assumed facts.

## 1. Executive Summary

### Overall conclusion

The current feature is a **class-first, single-class-per-upload UI** with a considerably stronger server-side write path than the UI suggests. It already has several important controls:

- A teacher's visible classes come from `class_subjects.teacherId`.
- Subjects shown for a selected class come from the exact `(className, subjectId, teacherId)` assignment query.
- The `submit_bulk_grades` RPC derives the authenticated actor, student class, subject name, parent, and assigned teacher on the server.
- The RPC validates the assessment allowlist and maximums, rejects duplicate records in one payload, previews existing classified records, and writes in one database function call.
- A partial unique index isolates a grade by `studentId + subjectId + examType + assessmentLabel + termId`, so Arabic and Tarbiya do not share a key.

However, the current design is not practical for the real multi-class teacher scenario:

- The teacher must repeat the configure/download/upload/preview/commit cycle once per class. For Arabic + Tarbiya across four classes, the current efficient path is **four uploads**, not one upload.
- The workbook has no class column, class sheet, upload manifest, or server-bound selected-class scope. Class is external UI context; the server derives class from each student ID.
- The downloaded teacher template contains headers only, not the selected class roster. Teachers must manually populate student IDs and names.
- All 11 assessment blocks are fixed for every subject. Assessment-block selection is not implemented.
- The server returns counts or the first error, not a complete row-level validation report grouped by class, subject, student, assessment, and source row.
- Existing grades are replaceable after confirmation, but the preview does not show old versus new values, approval status, class/subject breakdown, or a record-level replacement list.
- The RPC is atomic, which is good, but its per-record database lookups and repeated JSON duplicate scan are likely to become slow at the requested production volumes.
- The final database authorization logic is strong for the bulk RPC **if the 20260802 migration is deployed exactly as checked in**. The repository also contains broad legacy RLS policies and no visible RLS policy for `class_subjects`; the live grants and policies must be verified before calling the system production-secure.

### Recommendation in one sentence

Implement a **teacher-scoped multi-class wizard that generates one workbook with one worksheet per selected class**, with each sheet containing only that class's exact authorized subject assignments and selected assessment blocks; validate the complete workbook server-side before an atomic, explicitly confirmed commit.

This is a **C + D hybrid**: Workflow C for the selection and authorization model, and Workflow D for safer spreadsheet structure.

### Explicit scenario answer

For a teacher assigned to Arabic and Tarbiya in Grade 5A, Grade 5B, Grade 6A, and Grade 6B, the future workflow should be:

1. The teacher opens Bulk Upload Grades. The page identifies the signed-in teacher and displays only their authorized assignment matrix.
2. The teacher selects **Grade 5A, Grade 5B, Grade 6A, Grade 6B** using four checkboxes or Select All.
3. The system loads the exact `class_subjects` rows for that teacher and shows Arabic and Tarbiya for each class separately. It must not infer a Cartesian product.
4. The teacher selects Arabic and Tarbiya only where the matrix says the pair is assigned.
5. The teacher selects the needed assessment blocks, for example `HW1`, `CPW1`, `Attendance`, and `MT`.
6. The system generates one workbook with four class worksheets. Each sheet is prefilled with the enrolled roster and contains only the valid subject blocks for that class. Student IDs and names are generated by the system; the teacher does not type internal IDs.
7. The teacher fills one file and uploads it once. The server validates every row against the authenticated teacher, current assignment matrix, student enrollment, term, assessment definition, and overwrite policy.
8. The teacher sees a complete preview, including new and replacement values, then explicitly confirms. One transaction commits all valid records, or no records are committed if any blocking error remains.

This reduces the current four uploads to **one upload** without weakening class/subject authorization. It also makes it visually difficult to move Grade 5A's scores into Grade 5B because each class has its own generated sheet and roster.

### Current data flow

```text
Authenticated Supabase session
        |
        v

        |
        v
class_subjects.teacherId
        |                     \
        |                      -> selected class subjects for template

```

The browser sends only normalized grade records to the RPC. It does **not** send `teacherId`, `parentId`, subject display name, or approval status. The server derives those values.

### Current routes and roles

- Teacher: `/teacher/bulk-grades`
- Admin: `/admin/bulk-grades`
- There is no supervisor bulk-grade route in `App.tsx`.
- The admin page can select all classes and all mapped subjects for a class, but the server still limits the assignment target to a class/subject mapping with a non-null teacher.

### Current teacher workflow

The visible workflow is:

1. Load the current term and classes.
2. For a teacher, classes are the distinct `className` values returned by `class_subjects` rows where `teacherId = session.userId`.
3. Select one class using a row of buttons. The first class is selected automatically.
4. Load the selected class's assigned subjects and its student roster.
5. Open **Choose subjects** and select subjects for the example workbook.
6. Download one `Grades` worksheet containing the selected subjects' blocks.
7. Fill an Excel file and upload it.
8. The browser parses the first worksheet, resolves students against the selected class roster, resolves subject names against the selected class's authorized subjects, and shows client errors/warnings.
9. The teacher clicks **Review valid records**. This calls the server in preflight mode.
10. If the server reports existing records, the teacher sees an update count and confirms.
11. The teacher submits the same normalized payload with `p_confirm_updates = true`.

The class is selected once per workbook. There is no multi-select class control, no subject-per-class matrix, and no multi-sheet parsing.

### What the downloaded workbook actually contains

`downloadTemplate()` creates:

- One worksheet named `Grades`.
- Two header rows.
- `Student ID` and `Student Name` columns.
- One fixed 11-column block per selected subject.
- No student roster rows.
- No class column.
- No subject IDs.
- No term/month/date metadata.
- No upload manifest.

The public committed example workbook, `public/BulkUploadExample.xlsx`, contains seven subject blocks — English, Math, Science, Social, Somali, Arabic, and Tarabiya — and 77 grade columns, but no student data rows. The parser test confirms those seven subjects and 77 columns.

The generated filename includes the selected class, for example `BulkUploadGrades-Grade-5-A.xlsx`, but a filename is not an authorization boundary and is not sent to the server.

## 3. Current Teacher Workflow for the Arabic + Tarbiya Scenario

Assume the exact `class_subjects` assignments are:

| Class | Arabic | Tarbiya |
|---|---:|---:|
| Grade 5A | assigned to teacher | assigned to teacher |
| Grade 5B | assigned to teacher | assigned to teacher |
| Grade 6A | assigned to teacher | assigned to teacher |
| Grade 6B | assigned to teacher | assigned to teacher |

The current efficient use is:

| Upload | Current steps |
|---:|---|
| 1 | Select Grade 5A, choose Arabic + Tarbiya, download/fill/upload/review/confirm |
| 2 | Select Grade 5B, choose Arabic + Tarbiya, download/fill/upload/review/confirm |
| 3 | Select Grade 6A, choose Arabic + Tarbiya, download/fill/upload/review/confirm |
| 4 | Select Grade 6B, choose Arabic + Tarbiya, download/fill/upload/review/confirm |

So the teacher needs **four separate upload transactions**. If they choose only one subject in each workbook, the process expands to eight uploads, but that is not necessary because the current template supports multiple subjects for one selected class.

The teacher cannot accomplish the desired one-file workflow through the UI because:

- `selectedClass` is a single string, not an array.
- `getStudentsByClasses()` is called with `[selectedClass]`.
- `downloadTemplate()` accepts one class name and makes one `Grades` sheet.
- `parseExcel()` reads only `wb.SheetNames[0]`.
- There is no class/worksheet loop or cross-class selection state.

A direct RPC caller could submit records for several classes if every student/subject pair is currently assigned to that teacher, because the RPC derives each student's class and does not receive or enforce a UI-selected class scope. That is not an unauthorized-grade bypass when assignments are correct, but it is an important difference between the visible workflow and the actual server contract.

## 4. Workflow Comparison

| Workflow | Efficiency for this teacher | Class/subject safety | Fit with current schema | Audit result |
|---|---|---|---|---|
| **A. Class first** | Four uploads for the scenario; familiar | Good if server checks exact assignment | Direct fit | Current behavior; safe enough but unnecessarily repetitive |
| **B. Subject first** | Potentially two uploads, but each file spans four classes | Higher risk of class mixing unless the workbook is class-separated | Assignment data can support it, current UI cannot | Not recommended as a flat worksheet workflow |
| **C. Multi-class + multi-subject** | One selection, one validation, one commit | Strong if valid pairs are generated from exact mappings | Requires multi-class client/server scope | Best authorization and wizard model |
| **D. Separate upload sheets** | One file, but more sheet navigation | Strong visual class isolation | Requires multi-sheet parser and generated roster | Better than one flat sheet for preventing class mistakes |
| **Recommended: C + D** | One file and one commit | Exact assignment matrix plus class-separated sheets | Natural extension of `class_subjects` and student-derived class | Best production design |

A pure flat C workbook with a `Class` column is less safe than the C+D hybrid. A teacher can accidentally paste a student into the wrong class, and a class column is still client data. Separate generated class sheets provide a better human error barrier, while the server must continue to derive and verify class from `studentId`.

## 5. Audit of Grade Blocks and Validation

### Current assessment contract

| Workbook label | Stored `assessmentLabel` | Stored `examType` | Maximum | Representation |
|---|---|---|---:|---|
| `HW1 5` | `HW1` | `Homework` | 5 | Integer score 0–5 |
| `HW2 5` | `HW2` | `Homework` | 5 | Integer score 0–5 |
| `HW3 5` | `HW3` | `Homework` | 5 | Integer score 0–5 |
| `HW4 5` | `HW4` | `Homework` | 5 | Integer score 0–5 |
| `CPW1 15` | `CPW1` | `Classwork` | 15 | Integer score 0–15 |
| `CPW2 15` | `CPW2` | `Classwork` | 15 | Integer score 0–15 |
| `CPW3 15` | `CPW3` | `Classwork` | 15 | Integer score 0–15 |
| `CPW4 15` | `CPW4` | `Classwork` | 15 | Integer score 0–15 |
| `Att 20` | `ATTENDANCE` | `Attendance` | 20 | Integer score 0–20 |
| `MT 20` | `MT` | `Quiz` | 20 | Integer score 0–20 |
| `Akhlaaq 10` | `AKHLAAQ` | `Discipline` | 10 | Integer score 0–10 |

The CPW3 row above should be read as the same `Classwork` mapping as CPW1/2/4; the implementation in `ASSESSMENT_DEFINITIONS` is correct for all four CPW labels.

### Attendance is not a presence/absence field in this upload

The bulk grade `Attendance` block is a numeric integer with a hard maximum of 20. It is stored as an exam with `examType = 'Attendance'`, `assessmentLabel = 'ATTENDANCE'`, and `total = 20`.

This is separate from the daily attendance feature:

- `attendance` table rows use `present`, `absent`, or `late`.
- `RecordAttendance.tsx` writes daily status rows to that table.
- The bulk grade workbook does not encode present/absent/late statuses; `Absent` in a grade cell means an explicit non-scored exam entry, not a daily attendance status.

This distinction should be made very prominent in the future UI because “Attendance” currently names two different data concepts.

### MT is not stored as Midterm

The workbook's `MT` block is stored as `examType = 'Quiz'`, not `Midterm`. The broader application also has a `Midterm` exam type. The bulk contract is internally consistent, but the label is potentially confusing for teachers and reporting. The future design should display the school-facing meaning and the stored mapping clearly, or introduce a domain-specific assessment definition rather than relying on the broad `examType` string.

### Empty and special cells

The parser behavior is:

- Numeric `0`: a real scored zero.
- Blank or `-`: no record is generated.
- `Absent`: an explicit record with `entryState = 'absent'` and `score = null`.
- `N/A`, `NA`, or `Not applicable`: an explicit record with `entryState = 'not_applicable'` and `score = null`.
- Decimal, negative, malformed, and partial numeric values such as `3.5`, `-1`, and `5oops`: rejected by the browser parser.
- The server repeats the integer, score/state, total, assessment-label, and maximum checks, so changing the client payload cannot change a maximum or turn a decimal into a valid score.

### What is validated today

| Case | Current result |
|---|---|
| Unknown student ID | Client error if not in the selected class roster; server error if the ID does not exist |
| Student from another class | Client error in the class-first UI; server derives the student's actual class and checks its assignment |
| Missing student rows | Not an error. The upload can be a subset of the roster; there is no completeness warning |
| Duplicate student ID rows | Client error; server also rejects duplicate normalized records |
| Duplicate row with same student/subject/assessment/term | Client duplicate issue or server `unique_violation` |
| Duplicate subject block | Exact normalized duplicate subject is rejected by parser; aliases that resolve to the same subject can reach the duplicate-record check |
| Invalid subject name | Client subject binding error; server only accepts a valid `subjectId` that exists and is assigned for the derived class |
| Unauthorized subject | Server rejects unless the authenticated teacher is the current assigned teacher for the student's class and subject |
| Invalid class name | There is no class column to validate. Class is derived from `students.className` |
| Invalid class/subject pair | Server rejects because the exact mapping is missing or belongs to another teacher |
| Invalid assessment label/type/maximum | Server rejects with the fixed allowlist and map |
| Score above maximum | Rejected in browser and server; never clamped |
| Negative score | Rejected in browser and server |
| Decimal score | Rejected in browser and server |
| Entirely blank subject block | Client error; teacher must remove it or enter/mark a value |
| Additional worksheet | Ignored because only the first worksheet is parsed |
| Student name mismatch with valid ID | Name is informational; the ID is authoritative. A mismatch is not reported |
| Row with ID but blank name | Accepted by the parser even though the UI says new uploads require both ID and name; the server needs only the ID |

### Parser weakness: maximum-header check

`headerMentionsWrongMaximum()` tries to distinguish the ordinal in `HW1`/`CPW1` from the maximum. In doing so, a header such as `HW1 1` can be accepted because `1` is treated as the assessment ordinal, even though the approved maximum is 5. Similar ambiguity exists for CPW labels. This does not currently let a caller write an invalid maximum because the normalized record uses the fixed definition total and the RPC rechecks it, but it weakens template validation and can confuse teachers.

### Parser weakness: no complete server error set

The parser accumulates many browser errors, but the server RPC raises immediately on the first invalid record. A workbook with five server-side problems does not receive five actionable errors. The UI shows a toast containing one RPC message and does not map it to a source row, cell, class, or student.

## 6. Authorization and Security Findings

### What is correctly enforced by the bulk RPC

`submit_bulk_grades` derives:

- `v_actor_id` from `current_profile_id()` / `profiles.auth_id = auth.uid()`.
- `v_role` from `current_profile_role()`.
- Student class and parent from the `students` row identified by `studentId`.
- Subject name from the `subjects` row identified by `subjectId`.
- Assigned teacher from `class_subjects` for the derived student class and subject.

For a teacher, the RPC requires the assigned teacher to equal the authenticated actor. It does not trust a client-supplied teacher ID, subject display name, parent ID, status, or approval field.

A direct caller may change `studentId`, `subjectId`, `assessmentLabel`, `examType`, `total`, `termId`, month, date, score, or entry state, but the server independently validates the resulting target and values.

### Required four-class test matrix

Assuming the eight assignment rows in the scenario actually exist and each referenced student is enrolled in the named class:

| Attempt | Expected server result | Reason |
|---|---|---|
| Grade 5A + Arabic | PASS | Exact `class_subjects` row belongs to actor |
| Grade 5A + Tarbiya | PASS | Exact row belongs to actor |
| Grade 5B + Arabic | PASS | Exact row belongs to actor |
| Grade 5B + Tarbiya | PASS | Exact row belongs to actor |
| Grade 6A + Arabic | PASS | Exact row belongs to actor |
| Grade 6A + Tarbiya | PASS | Exact row belongs to actor |
| Grade 6B + Arabic | PASS | Exact row belongs to actor |
| Grade 6B + Tarbiya | PASS | Exact row belongs to actor |
| Grade 7A + Arabic | FAIL | No actor assignment for the derived student class/subject |
| Grade 6A + Mathematics | FAIL | No actor assignment for Mathematics in 6A |
| Grade 7B + Tarbiya | FAIL | No actor assignment for the derived class/subject |
| Another teacher's class | FAIL | `v_teacher_id <> v_actor_id` |
| Another teacher's subject | FAIL | Exact mapping belongs to another teacher |

This matrix was reviewed against the SQL authorization path, but it was **not executed against a live database** in this checkout.

### Authorization gaps and risks

#### High: `class_subjects` RLS is not visible in the repository

The schema and migrations define `class_subjects` indexes and reads, but there is no visible `ALTER TABLE public.class_subjects ENABLE ROW LEVEL SECURITY` or class-subject policy. If the live API grants authenticated users direct table writes, a malicious teacher could attempt to insert/update an assignment row for themselves. The bulk RPC would then correctly enforce the now-modified assignment, but the assignment table itself would have been compromised.

The live database must be checked for:

- RLS enabled on `class_subjects`.
- Authenticated/anon table grants.
- Admin-only insert/update/delete policies.
- A unique active assignment constraint.

The UI hiding assignments is not enough.

#### High: broad legacy student policy remains in the checked-in full schema

`supabase-schema.sql` creates `"Allow all operations on students"` with `USING (true)`. Later migrations add more restrictive-looking policies, but PostgreSQL permissive policies are combined with OR. Unless the broad policy was removed in the live database, it can allow much wider student reads and writes than intended. This is not a direct bypass of the bulk RPC's grade checks, but it is a serious system-level security and roster-integrity issue that can affect the data the grade authorization relies on.

The same full schema creates broad profile access. The live policy set must be audited, not inferred from the names of later policies.

#### Medium: UI-selected class is not a server-bound batch scope

The RPC checks each record's derived class/subject assignment but does not receive a selected class set. A raw caller can submit authorized records from several classes in one call. That is acceptable for the recommended future multi-class workflow, but the current UI implies one class and does not explicitly show or audit a multi-class selection. The future API should use a server-issued upload manifest or explicit selected assignment set so the preview and commit scope are the same object.

#### Medium: `class_subjects` duplicate rows are possible

There is no unique constraint on `(className, subjectId)` or on an active assignment. The RPC uses `LIMIT 1` to select the teacher. If duplicate mappings exist, authorization becomes dependent on which row PostgreSQL returns. A unique active assignment constraint is required.

#### Medium: term selection is not restricted to the current term on the server

The UI loads `getCurrentTerm()`, but the RPC accepts any existing `termId` whose date/month rules pass. A direct teacher caller can target another valid term, including an old term, unless a separate live policy prevents it. If historical corrections are intended, that must be an explicit product rule; otherwise server-side current-term or period-lock authorization is missing.

### Tampering results

| Tampered input | Can it bypass the bulk RPC? | Finding |
|---|---|---|
| `teacherId` | No | Not accepted as an authority; server derives teacher |
| Subject display name | No | Server derives name from `subjectId` |
| `subjectId` | No, for unauthorized assignments | Must exist and map to the student's class and actor |
| `studentId` | No, for nonexistent or unauthorized target | Student class is looked up server-side |
| Class name in spreadsheet | No class field exists | Class is derived from student; future class/sheet metadata must remain advisory only |
| Assessment label/type | No | Fixed server allowlist and pair validation |
| Maximum score | No | Fixed label/type/total map and score range check |
| Academic year/term | Partially | Invalid term is rejected, but any valid term appears selectable through a raw RPC call |
| Existing grade | Not silently on first request | Preflight reports an update count; commit replaces after confirmation |

## 7. Database and Data Integrity Findings

### Current schema protections

The intended post-migration `exams` table has:

- Foreign key from `studentId` to `students`.
- Foreign key from `subjectId` to `subjects` added by the bulk integrity migration.
- Foreign key from `termId` to `terms` added by the bulk integrity migration.
- Foreign key from `teacherId` to `profiles`.
- Foreign key from `uploadedBy` to `profiles`.
- Check constraints for entry state, score/state compatibility, assessment label, exam type, and approved maximums.
- Partial unique index:

```text
(studentId, subjectId, examType, assessmentLabel, termId)
WHERE subjectId IS NOT NULL
  AND termId IS NOT NULL
  AND assessmentLabel IS NOT NULL
```

The identity correctly keeps these records separate:

```text
same student + Arabic  + MT + term -> one key
same student + Tarbiya + MT + term -> different key
5A student + Arabic + HW1 + term   -> different from 5B student + Arabic + HW1 + term
```

Akhlaaq is therefore stored per subject, not as one student-wide discipline row. Uploading Tarbiya Akhlaaq cannot conflict with Arabic Akhlaaq when both use their correct `subjectId`.

### Existing grade behavior

The server performs a no-write preflight when `p_confirm_updates = false`:

- Counts existing classified identities.
- Returns `insertCount` and `updateCount`.
- Sets `requiresConfirmation` if any update is found.

On confirmation:

- The upload is upserted by the unique identity.
- Existing score, total, entry state, month, date, status, parent, teacher, and uploader fields can be replaced.
- `status` is reset to `pending` on update.
- An idempotency row is stored in `grade_uploads`.

This is safer than blind inserts, but the teacher does not see the old score, new score, class, subject, assessment, or approval status for each replacement. The safest future default is:

- New records: commit after validation.
- Existing records: show old/new values and require a clearly named **Replace Grades** confirmation.
- Optionally default to rejecting existing records unless the teacher explicitly enables replacement.
- Keep a durable change/audit record for every replacement.

### Important legacy duplication risk

The unique index and preflight only cover rows with a non-null `assessmentLabel`, `subjectId`, and `termId`. Historical homework/classwork rows may have a null `assessmentLabel`; the migration deliberately leaves them for review. A new classified bulk row can therefore coexist with an older unclassified row for the same student/subject/term/type. This can create duplicate historical data or double counting unless the historical duplicate view is reviewed and reporting logic handles the distinction.

### Class is not part of grade identity

For currently enrolled students, this is normally correct because `studentId` identifies the student and the student's current class is derived. It means class is not an independent enrollment-period dimension. If students can move between classes within an academic term and grades must remain attached to a class enrollment, the model needs a student-class enrollment/roster history table and the grade identity must include the enrollment or assignment context.

### Month is not part of grade identity

The UI and payload include both `month` and `termId`, but the unique identity and preflight join use `termId` and do **not** use `month` or `date`. Therefore a second upload of the same student, subject, assessment label, and term in a different month replaces the first one. This is correct only if HW1/CPW1/MT are deliberately term-scoped slots. If the school's labels repeat monthly, this is a high-risk overwrite bug; the identity must include the intended month/assessment period. The product must make this scope explicit rather than showing month as if it were part of the grade identity.

### Database model gaps

- No class table or FK; `students.className` and `class_subjects.className` are free text.
- No uniqueness constraint for a class/subject mapping.
- No visible RLS boundary for `class_subjects`.
- Subject names are not declared unique; client aliases can be ambiguous.
- The checked-in full schema and migration history have drift: the full schema describes a baseline while later migrations add important FKs, constraints, roles, and functions. Production verification must use `pg_get_functiondef`, `pg_policies`, `information_schema`, and `pg_indexes` rather than relying only on `supabase-schema.sql`.

## 8. UX Findings

### What works

- The flow has an explicit preflight and confirmation stage.
- The teacher can select multiple subjects for one class, which avoids eight uploads in the scenario.
- The UI never asks the teacher to type a subject ID.
- Student IDs are the preferred identity and name-only legacy files require manual confirmation for ambiguous matches.
- Zero, absent, and N/A semantics are documented in the parser behavior and tested.
- The final button distinguishes new records from updates.

### Main usability problems

1. **The teacher's identity is not prominent.** The page does not show “Uploading as [teacher name]”.
2. **Only one class can be selected.** The primary real-world scenario requires four repeated cycles.
3. **Subject selection is a template helper, not a real upload scope.** A workbook can contain assigned subjects not selected in the menu; the menu is not compared to the uploaded block set.
4. **No exact assignment matrix is shown.** A global list of subjects cannot communicate that Arabic may be assigned in one class but not another.
5. **The downloaded workbook has no roster.** Teachers must source IDs and names separately and can easily omit students or mistype an ID.
6. **The file has no visible class identity beyond its filename.** The filename is easy to change and is not parsed.
7. **All assessment blocks are always present.** Teachers cannot generate a focused HW1/MT-only file.
8. **The preview is not a true upload preview.** It shows row resolution and counts, but not classes affected, subjects affected, distinct students, new records, rejected rows, or old/new replacement values.
9. **Errors are not grouped by the requested dimensions.** The client list is flat; server errors are generally one toast.
10. **Missing students are silent.** A teacher can upload only 18 of 25 roster students without a completeness warning.
11. **A valid ID hides a name mismatch.** This is safe for identity but can conceal a copy/paste mistake.
12. **The term/month default can be wrong.** Month initially uses the browser's current month before the current term's month list is loaded; the server eventually rejects invalid month/term combinations, but the user experience is avoidably confusing.
13. **The two meanings of Attendance are not explained.** Numeric 0–20 grade attendance is different from daily present/absent/late attendance.

## 9. Performance Findings

### Current client behavior

- The selected class roster is fetched in one request with a limit of 10,000.
- The assignment/subject context is fetched separately.
- Parsing is done synchronously in the browser after reading the whole workbook into memory.
- The preview renders one table row per student row, which is acceptable for ordinary classes but should be virtualized or paginated for very large workbooks.
- The browser sends one RPC request for preflight and one for commit, not one HTTP request per grade cell.

### Current server behavior

Inside `submit_bulk_grades`, each JSON record is processed in a loop. For every record it performs lookups for:

- Student and class/parent.
- Subject name.
- Term/date/month configuration.
- Class/subject teacher assignment.
- Duplicate detection against all prior normalized JSON records.

The duplicate check scans `jsonb_array_elements(v_normalized)` for every record, which is O(n²) in the number of records. The final commit also loops and executes one upsert per normalized record. The existing indexes help lookup and conflict detection, but they do not remove the repeated procedural work.

### Requested volume assessment

These are static capacity findings, not measured timings because dependencies and a live database were unavailable.

| Workload | Current path | Assessment |
|---:|---|---|
| 50 grade records/cells | Parser + RPC | Expected to be fine |
| 500 | Parser + RPC | Likely acceptable; still one procedural loop |
| 1,000 | Parser + RPC | Should be tested in staging; likely acceptable but no benchmark exists |
| 5,000 | Parser + RPC | Meaningful risk of slow preflight/commit due to per-record lookups and JSON duplicate scan |
| 10,000 | RPC hard limit | Accepted at the limit if all other constraints pass; likely slow and memory-heavy |
| More than 10,000 nonblank grade records | RPC rejects | Current teacher must split the upload, with no single upload transaction across the splits |
| 10,000+ grade cells but <=10,000 records | Possible | File size, browser memory, and server execution time still need staging measurement |

The migration limit is 10,000 **grade records**, not 10,000 students or rows. For example, 1,300 students × 2 subjects × 11 nonblank blocks equals 28,600 records and cannot be committed as one current RPC call.

### Recommended performance design

- Parse workbook once, then send a compressed normalized payload or upload to a short-lived staging table/object.
- Use `jsonb_to_recordset()` or a typed staging table for set-based validation.
- Resolve students, subjects, terms, and assignments with joins, not one query per record.
- Use a temporary or persisted upload-staging table keyed by `upload_id` for large files.
- Enforce a reasonable maximum based on measured staging capacity; if chunking is required, make server-side staging plus one final commit the atomic unit. Do not ask the browser to commit independent chunks while claiming the upload is atomic.
- Add timing and row-count telemetry to `grade_uploads` or a dedicated upload audit table.

### Why not rely on a class column?

A class column is useful for diagnostics but must not be trusted. A teacher can edit it. A separate sheet improves human safety, while the server must verify:

```text
student_id -> enrolled/current class -> selected assignment -> subject -> teacher
```

### Student identification

Use `Student ID` as the required identity. Prefill it as text so leading zeros are preserved. Include `Student Name` as a read-only confirmation field. A name mismatch should be a warning or error according to policy, not an invitation to remap a valid ID by fuzzy matching.

Name-only legacy uploads should be retired or placed behind an explicit “legacy import” mode with strong duplicate-name handling.

## 12. Recommended Authorization and Database Changes

These are future implementation recommendations only; none were applied in this audit.

### Assignment model

1. Treat the exact active assignment relation as authoritative: teacher + class + subject, optionally scoped to academic year/term.
2. Add a unique active constraint for `(class, subject, academic_period)` and prevent multiple active teachers unless co-teaching is intentionally supported.
3. Protect `class_subjects` with RLS and admin-only management policies.
4. Add a class table or controlled class reference rather than free-text class names.
5. Consider an enrollment table if a student can change class during a term.
6. Make subject names unique or use a normalized subject identity; avoid ambiguous aliases as a security mechanism.

### RPC/staging architecture

Use two server operations or one server-issued draft flow:

1. `create_grade_upload_draft(selection)`
   - Derives actor from `auth.uid()`.
   - Computes exact authorized class/subject pairs.
   - Snapshots the roster and term/block scope.
   - Returns a non-guessable upload ID and manifest.
2. `validate_grade_upload(upload_id, normalized_records)`
   - Performs set-based validation.
   - Returns every row error and counts.
   - Writes no `exams` rows.
3. `commit_grade_upload(upload_id, payload_hash, replace_existing)`
   - Re-checks actor, assignment, roster, term, and manifest.
   - Refuses changed or stale assignment scopes unless explicitly regenerated.
   - Commits all grade rows and audit data in one transaction.

The existing preflight/commit RPC is a good safety direction, but it should be extended rather than bypassed. Any direct `exams` write path must remain separately authorized or be routed through the same domain checks.

### Grade identity and overwrite policy

Retain or formalize:

```text
student_id + subject_id + assessment_label + academic_period
```

`examType` can remain a checked denormalized field, but the domain assessment definition should be authoritative. Add an audit/change table for replacements with:

- upload ID
- actor
- old score/state/status
- new score/state/status
- student, subject, assessment, term
- timestamp

Default behavior should be **no overwrite without explicit confirmation**. If policy allows teacher corrections, the preview must list every replacement. Approved grades should require additional permission or an admin review path.

### RLS and policy verification

Before production rollout, verify the live database for:

```sql
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('class_subjects', 'students', 'subjects', 'exams', 'grade_uploads');

select * from pg_policies
where schemaname = 'public'
  and tablename in ('class_subjects', 'students', 'exams', 'grade_uploads');
```

Also inspect live function definitions and grants. The source contains both baseline schema policies and later migrations; the live result is what matters.

### Indexes

The current grade identity index is useful. Also consider:

- `class_subjects(teacherId, className, subjectId)`.
- `class_subjects(className, subjectId, teacherId)`.
- `students(className, id)` or an enrollment equivalent.
- `exams(studentId, subjectId, termId, assessmentLabel)`; the existing lookup index is close to this.
- A unique index for active assignment mappings.

## 17. Remaining Risks

Even after the recommended wizard is implemented, the following must remain server concerns:

- Spreadsheet protection is not security; users can edit files and IDs.
- A student can change classes, so class/enrollment history must be defined.
- Assignment changes during an open upload can make the generated template stale; the commit must revalidate or expire the manifest.
- Approved-grade replacement needs a permission policy, not only a confirmation button.
- The daily attendance table and numeric Attendance grade block must not be accidentally merged in reporting.
- Legacy exam rows without assessment labels need a controlled migration/reconciliation process.
- A large one-file upload may exceed the current RPC record limit; staging and one final transaction are required if the school wants a single atomic upload beyond 10,000 grade records.

## Final Recommendation

The current class-first model is acceptable for a teacher who teaches one class, but it is not the right primary workflow for a teacher who teaches the same subjects across several classes.

Adopt **multi-class selection plus exact per-class subject assignment**, and generate **one workbook with one worksheet per class**. For the Arabic/Tarbiya teacher:

```text
Select 4 classes
  -> select the 8 authorized class/subject pairs
  -> select assessment blocks
  -> generate four prefilled class sheets
  -> fill one workbook
  -> validate one complete batch
  -> review new/replaced/rejected counts and row details
  -> commit once, atomically
```

The server must independently verify every record using:

```text
current_user
  -> teacher profile
  -> exact class_subject assignment
  -> student ID and derived class
  -> subject ID
  -> assessment definition
  -> academic period
  -> overwrite policy
```

A teacher must never be authorized because a class name, subject name, teacher ID, sheet name, or spreadsheet value merely looks valid.
