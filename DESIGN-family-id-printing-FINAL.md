## 1. Audit of the existing implementation

### 1.1 Schema — no `families` table, and none is needed

A family is a derived grouping keyed by a string on `students` (`20260802_family_ids.sql:16-30`):

| Column | Meaning |
|---|---|
| `govId` | Sheet `numberGov` |
| `transport` | bus number \| `WALKER` \| `CAR` \| `LEFT` (CHECK, `NOT VALID`) |
| `parentPhone` | Sheet `SECOND NUMBER`, normalized |
| `familyId` | 4-digit zero-padded string, indexed. `MBK-` is display-only (`displayFamilyId`) |

Related: `release_log` (gate handoffs), `audit_logs`. **No print/card state exists anywhere** — `grep -i print supabase/` yields one comment.

**Verdict on a `families` table: reject.** Nothing in this work needs it; introducing it would force a data migration plus rewrites of `generate_family_ids`, `lookup_family`, `record_release`, the gate, and the parent portal. Both reviews agreed; the audit confirms it.

### 1.2 Generation

`generate_family_ids(p_transport_filter TEXT DEFAULT NULL)` — SECURITY DEFINER, admin-only, audit-logged. Candidates are `WHERE familyId IS NULL AND transport <> 'LEFT'`, grouped by `parentId` → else `normalize_phone(parentPhone)` → else unattached. Number = `MAX(existing)::INT + 1`, `lpad(…,4,'0')`.

**Four definitions exist**, applied in lexicographic order:

```
20260802_family_ids.sql               → generate_family_ids()            [0-arg]
20260802_fix_family_ids_generator.sql → generate_family_ids()            [0-arg]
20260802_generate_transport_filter.sql→ generate_family_ids(TEXT DEFAULT)[1-arg]  ← newest logic
20260802_mark_student_left.sql        → generate_family_ids()            [0-arg]  ← applied LAST
```

No `DROP FUNCTION` anywhere. So Postgres holds **two overloads**, and the 0-arg body applied last is an **older body without the transport filter**. Two live consequences:

1. `generateFamilyIds()` (the "All" path) sends `rpc('generate_family_ids', {})` → ambiguous, or silently binds the 0-arg legacy body.
2. Even if it binds, that body predates the filter feature.

This is a genuine landmine. Both reviews flagged it; **both were right, and it is more serious than either stated** (it is not merely "duplicate definitions", it is *stale logic applied last*).

### 1.3 Import

`transportImport.ts` (XLSX/CSV/paste, header-name mapping, name-first matching, ambiguity flags) → `applyTransportImport()` → per-row `set_student_import_fields()` RPC writing `govId`, `transport`, `parentPhone`. **Import never writes `familyId`** — verified.

### 1.4 UI and print

`src/pages/admin/FamilyIds.tsx` — **936 lines, one component**, linear wizard: help → stats → progress → *1 Generate* → *2 Import* → *3 Families* → *4 Print*, plus unattached and left buckets. The families table has **no search, no filters, no sort, no selection, no per-row actions**, in a `max-h-96` scroll box.

Print: `AsyncPrintLink` takes `filteredFamilies` (whole list, narrowed only by one transport select) → `getParentNames()` → `buildFamilyCardData()` → `pdf(<FamilyCardsDocument/>)` → iframe preview or download. Three layouts; QR as a vector path; front+back pages; optional gate lookup list.

**Coupling verdict:** no print path calls a write RPC — printing is *technically* already incapable of generating. But it is *structurally* coupled: it is step 4 of a Generate-first wizard with all-or-transport-filter granularity only.

### 1.5 Permissions — the effective matrix

Derived from every policy across all migrations:

| Role | `students` SELECT | `profiles` SELECT |
|---|---|---|
| admin | **all** | **all** |
| office | **all** (`Office can read all students`) | own only |
| supervisor | **only `assignedClasses`** (shares the "Teachers can read…" policy) | own only |
| teacher | only `assignedClasses` | own only |
| parent | own children | own only |

`canAccessRoute()` exists in `src/lib/routing.ts` but **is never called at runtime** — routing is a per-role `switch` in `App.tsx`. It is tested, not enforced. Not a vulnerability today (the switches happen to match), but it is a trap.

## 2. FINDINGS — verified, with severity

### 🔴 F1 (NEW — neither review found this) — Generation splits a family when a sibling enrols later

`generate_family_ids` groups **only students whose `familyId IS NULL`** and then **unconditionally allocates a fresh number** (`v_next_id := v_next_id + 1`). It never asks "does a student with this same `parentId`/phone already have a `familyId`?"

Simulated against the live body:

```
After first Generate:
  Xalimo(parent=p1) → 0001
  Ahmed (parent=p1) → 0001
New sibling Yasmin enrols (parent=p1); admin runs Generate:
  Xalimo → 0001 · Ahmed → 0001 · Yasmin → 0002
  >>> ONE physical family now holds TWO family IDs
```

**Why this is the most important finding in this document.** The design's stated premise is *"The family is the unit of identity — siblings share one family ID."* At the gate, the parent presents card `MBK-0001`; `lookup_family('0001')` returns **two of the three children**. The third is invisible. That is precisely the class of failure — a child unaccounted for at dismissal — that this project exists to eliminate.

It is also silent: no error, no warning, and the admin page's "Families" count simply increments.

Both reviews asserted "generation is idempotent / IDs are stable." That is true **per student** and false **per family**. Neither tested the sibling case.

### 🔴 F2 (both reviews, confirmed) — `mark_student_left()` destroys the Family ID

`mark_student_left(true)` sets `transport='LEFT'` **and `familyId = NULL`**. Restore sets `transport=NULL` and leaves `familyId` NULL. Next Generate issues a **different** number:

```
Kid A → 0001, Kid B → 0001
mark left(B):        A → 0001, B → NULL
restore(B) + Generate: A → 0001, B → 0002   ← B split out of their own family
```

Same failure mode as F1, reachable from a UI button. Review B named this specifically; Review A mentioned it only in passing. **Review B was more right.**

### 🔴 F3 (both reviews, confirmed) — Supervisors print incomplete cards; nobody but admin gets parent names

Card data comes from `getStudents()` (plain REST, RLS applies) and `getParentNames()` (reads `profiles`).

* A **supervisor** sees only students in `assignedClasses` → prints a family card **missing siblings**, with no error. A card that under-lists a family is actively dangerous at a dismissal gate.
* **Office and supervisor cannot read `profiles`** → `parentName` silently prints as `—` on every card they produce. Office is the *primary* printing role, so in practice **today's cards are printing without a parent name**.

Also: `buildFamilyCardData` uses the raw sheet `parentPhone`, while the gate's `lookup_family` prefers `profiles.phone1/phone2`. **The card and the gate can display different phone numbers for the same family.** Neither review caught this inconsistency.

### 🟠 F4 (both reviews, confirmed) — Duplicate/stale `generate_family_ids` overloads

See §1.2. Must be resolved before any further work on the generator.

### 🟠 F5 (both reviews, confirmed) — Mixed-transport families mis-filtered and mis-labelled

`FamilyIds.tsx:126` filters on `students[0]?.transport`; `familyCards.tsx:277` prints the badge from `students[0]`. A family with a walker and a bus rider is bucketed and labelled by whichever child sorts first.

### 🟠 F6 (Review A only, confirmed) — The families table cannot support the requested workflow

No search/filter/sort/selection/pagination at the 200-family target. This is the actual UX blocker for every use case in the brief.

### 🟡 F7 — `canAccessRoute()` is dead code

Exported and unit-tested, never called. Route access is duplicated in `App.tsx` switches.

### 🟡 F8 — `audit_logs` is world-readable **and** world-insertable

`00001_create_audit_logs.sql:13,18` — `USING (true)` / `WITH CHECK (true)` for all authenticated. Any parent can read `family_ids.*` events and forge entries. This rules out `audit_logs` as a trustworthy print history.

### ✅ F9 — REFUTED: duplex misalignment on partial pages

**Both reviews claimed this; it is false.** I rendered real PDFs and extracted card rectangles:

```
=== 1 card ===   0001: front=212.6 back=212.6 need=212.6 ok        VERDICT ALIGNED
=== 3 cards ===  0002: front=306.1 back=119.1 need=119.1 ok
                 0001: front=119.1 back=306.1 need=306.1 ok
                 0003: front=212.6 back=212.6 need=212.6 ok        VERDICT ALIGNED
=== 5,6,7,9 cards ===                                              VERDICT ALIGNED
```

**Why the code review was wrong.** `mirrorForLongEdge` does reverse rows in place, so a lone card's *array position* is unchanged — that is what both reviews saw. But `gridPage` uses `justifyContent: 'center'`, so a partial row is **centred**, and a centred card is its own mirror image:

```
single card centred x = 212.6 ;  A4 − (212.6 + 170.1) = 212.6  →  self-mirroring
```

The layout engine cancels the apparent bug. **No fix is required, and "pad the rows" — which both reviews proposed — would actively break it** by left-aligning partial rows into a non-mirror-symmetric position.

**Lesson applied:** the only safe change here is to add a *regression test* locking the measured behaviour, so a future edit to `justifyContent` cannot silently break duplex output.

### ✅ F10 — REFUTED: PDF performance needs chunking / progress machinery

Measured, including the lookup list:

| Families | Time | Size | Pages |
|---|---|---|---|
| 1 | 0.22 s | 9 KB | 3 |
| 50 | 1.5 s | 168 KB | 27 |
| **143** | **3.5 s** | 468 KB | 73 |
| 250 | 6.4 s | 820 KB | 127 |

Node is slower than a warm browser. A full-school print is a **~3.5 s wait**. Review A's chunking-at-150 and batch-progress proposals are **unnecessary complexity** — a spinner and a disabled button suffice.

### ✅ F11 — REFUTED: big families overflow the card

1/3/6/8/12 children all render exactly 2 page objects — no overflow. A 6-row clamp (Review A) is **speculative**; drop it. Typography degrades past ~8 children, so a *visual* review is worth doing, but no code guard is needed for v1.

### ✅ F12 — Review A's "3 known pre-existing test failures" is stale

`npx vitest --run` → **260 passed, 35 files, 0 failures.** The green baseline is 260/260; any new failure is genuinely new.

## 3. The mental model — validated

**Printing is family-based. Student selection is an input mode, never an output unit.**

The user's assumption is correct and the data model proves it:

* The card carries one `MBK-####`, one QR encoding that ID, and the whole sibling list.
* The gate types a family ID; `lookup_family(familyId)` returns siblings. There is no student-level lookup.
* `release_log` records per-student releases, but the *credential* presented is the family card.

So the physical artifact is unambiguously the family. Student selection is how staff *think* when a request arrives class-by-class ("cards for my new G7A intake") — a resolver, not a second renderer.

**Encode it in the type system** so it cannot drift:

```ts
export type PrintSource =
  | { kind: 'families'; familyIds: string[] }
  | { kind: 'students';  studentIds: string[] };

export interface PrintBatch {
  families: FamilyCardData[];   // deduped, sorted — the ONLY thing that renders
  cardCount: number;
  duplicatesMerged: number;
  skippedNoFamilyId: Student[];
  skippedLeft: Student[];
}
export function resolvePrintBatch(source: PrintSource, roster: Student[]): PrintBatch;
```

`FamilyCardsDocument` accepts only `PrintBatch['families']`. Student-based printing becomes unrepresentable at the output stage.

## 4. Architecture decision: A vs B vs C

**Chosen: C — hybrid.** Table is the home; every path funnels through one shared Print Batch dialog.

| Criterion (weight for a school office) | A | B | C |
|---|---|---|---|
| Reprint one lost card — **the dominant job** | 3 clicks | 5–6 clicks + navigation | **3 clicks** |
| Print by students | awkward inside a family table | natural | natural (a tab) |
| Duplicate prevention disclosure | no natural home | batch screen | **one canonical place** |
| Discoverability for non-technical staff | good | must learn a 2nd destination | **good — one screen** |
| Error prevention on the 143-card run | none | review step | **review step** |
| Maintainability | 1 surface | 2 surfaces, duplicated table | **1 table + 1 dialog** |
| Mobile/tablet | table cramped | better | table + full-screen dialog |

Decisive reasoning for *this* school:

1. **The gate-adjacent reality is single reprints.** A parent at the counter, a lost card, one family. That must be ~3 seconds from a search box — row actions, not a separate destination.
2. **Bulk printing happens once or twice a year** and consumes an afternoon of card stock and lamination. It *should* cost one extra confirming click showing "143 cards · 73 pages".
3. **"By students" needs a different picker** and an explicit dedupe disclosure. A tab inside the shared dialog is exactly the right size — no second page to learn, no modal-within-a-table confusion.
4. **One code path** for resolution, counting, dedupe, preview, and the print-history write.

Review A said C, Review B effectively described A-with-a-setup-page. **A's architecture choice is correct; B's page-splitting instinct is also correct.** The final design takes both (§5).

## 6. Is print history necessary? — **Deferred. Not Phase 1.**

Review A made `family_card_prints` + two RPCs a Phase-1 requirement. On audit that is **over-engineering relative to the problem in front of us**, and it violates the user's explicit "avoid unnecessary database complexity."

What it would genuinely solve: "did this family ever receive a card?", "who printed the card found in the street?", "which families changed since their card was printed?".

Why it can wait:

* **None of the six requested capabilities need it.** Print one / several / all / by-students / reprint / search-and-print all work without any write.
* Reprint intent is not required for correctness — the output PDF is byte-identical whether it is a first print or a reprint.
* It is **purely additive later**: a new table plus one RPC call at the end of the existing print action. No refactor, no data migration, no change to the resolver or the renderer.
* It cannot be built on `audit_logs` (F8), so it is a genuine new table + RLS + tests — real cost.
* Phase 1 already contains **two safety-critical data-integrity fixes** (F1, F2) and a **correctness fix** (F3). Those deserve the review attention.

**Decision: Phase 2, and only if the office asks for it.** The one thing to do now is keep the door open — `resolvePrintBatch` returns the resolved family list, so wiring a logging call later touches exactly one function.

Review A: wrong to require it. Review B: right to call it optional ("possibly add").

## 7. Family-ID stability — the invariant

> **INVARIANT — one family key, one Family ID, forever.**
> For any grouping key *k* (`parentId`, else normalized `parentPhone`), all students resolving to *k* share exactly one `familyId`, and that value is allocated at most once for the lifetime of *k*. A Family ID is never re-issued, never re-numbered, and never abandoned while any student of *k* remains enrolled.

Today's implementation violates this in two places (F1, F2). Both fixes are small and server-side.

**Fix A — reuse an existing family's ID (F1).** Before allocating, resolve the group key against students who *already* have an ID:

```sql
-- inside the group loop, before v_next_id := v_next_id + 1
SELECT s."familyId" INTO v_existing
FROM public.students s
WHERE s."familyId" IS NOT NULL
  AND CASE
        WHEN v_group.family_key LIKE 'p:%'
          THEN 'p:' || s."parentId" = v_group.family_key
        ELSE 't:' || public.normalize_phone(s."parentPhone") = v_group.family_key
      END
LIMIT 1;

IF v_existing IS NOT NULL THEN
  v_family_id := v_existing;              -- join the existing family
ELSE
  v_next_id  := v_next_id + 1;            -- genuinely new family
  v_family_id := lpad(v_next_id::TEXT, 4, '0');
  v_created  := v_created + 1;
END IF;
```

Add `studentsJoined` to the returned summary so the UI can say *"2 new families · 1 student joined an existing family."*

**Fix B — stop destroying the ID (F2).** `mark_student_left` must **not** null `familyId`:

```sql
IF p_left THEN
  UPDATE public.students SET "transport" = 'LEFT' WHERE id = p_student_id;   -- keep familyId
ELSE
  UPDATE public.students SET "transport" = NULL   WHERE id = p_student_id;   -- ID intact
END IF;
```

**Coupled change, mandatory:** because LEFT students would now retain a `familyId`, they must be excluded where families are materialised — otherwise a departed child reappears at the gate:

* `lookup_family()` — add `AND COALESCE(s."transport",'') <> 'LEFT'`
* card roster building — same filter
* `groupStudentsByFamily()` — same filter

`generate_family_ids` already excludes LEFT candidates.

**Data repair:** a one-off audit query for families already split by F1/F2 (same `parentId` or phone, differing `familyId`), reconciled with the existing admin `assign_family_override()` — which merges by design. No new tooling required.

## 8. Permissions and data completeness — minimum safe fix

Do **not** widen table RLS (that would give supervisors read-all on students and everyone read-all on profiles). Use one SECURITY DEFINER RPC — the pattern already used five times in this feature:

```sql
CREATE FUNCTION public.get_family_cards(p_family_ids TEXT[])
RETURNS JSONB
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public
AS $$
  SELECT coalesce(jsonb_agg(fam ORDER BY fam->>'familyId'), '[]'::jsonb)
  FROM (
    SELECT jsonb_build_object(
      'familyId', s."familyId",
      'parentName',  max(pr.name),
      'parentPhone', max(COALESCE(
          NULLIF(public.normalize_phone(pr."phone1"), ''),
          NULLIF(public.normalize_phone(pr."phone2"), ''),
          NULLIF(public.normalize_phone(s."parentPhone"), ''),
          s."parentPhone")),
      'students', jsonb_agg(jsonb_build_object(
          'id', s.id, 'name', s.name, 'className', s."className",
          'transport', s."transport") ORDER BY s.name)
    ) AS fam
    FROM public.students s
    LEFT JOIN public.profiles pr ON pr.id = s."parentId"
    WHERE s."familyId" = ANY(SELECT public.normalize_family_id(x) FROM unnest(p_family_ids) x)
      AND COALESCE(s."transport",'') <> 'LEFT'
      AND public.current_profile_role() IN ('admin','supervisor','office')
      AND public.current_profile_id() IS NOT NULL
    GROUP BY s."familyId"
  ) t;
$$;
REVOKE ALL ON FUNCTION public.get_family_cards(TEXT[]) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.get_family_cards(TEXT[]) TO authenticated;
```

This single function fixes **all three** of F3's symptoms — complete sibling rosters regardless of role, parent names for office/supervisor, and phone resolution **identical to `lookup_family`** so the card and the gate never disagree. It is deliberately modelled on `lookup_family` so the two stay in step.

The table itself stays browsable via the existing RLS-scoped `getStudents()`; only the **printed artifact** goes through the RPC. Both reviews proposed a roster RPC; this is the concrete minimum.

**Final permission model**

| Action | admin | supervisor | office | teacher | parent |
|---|---|---|---|---|---|
| `/admin/family-ids` (browse, search, print) | ✅ | ✅ | ✅ | ❌ | ❌ |
| `/admin/family-ids/setup` (import, generate) | ✅ | ❌ | ❌ | ❌ | ❌ |
| Override / mark left / edit transport | ✅ | ❌ | ❌ | ❌ | ❌ |
| Own family card | — | — | — | — | ✅ (portal) |

Enforced in three places: `ROUTE_ACCESS` (**and actually call `canAccessRoute()`** — fixes F7), the role switches in `App.tsx`, and SQL role checks in every RPC.

## 9. Enforcing generation ≠ printing

Four mechanisms, defence in depth:

1. **Type-level.** `FamilyCardsDocument` consumes `PrintBatch['families']`, built only by `resolvePrintBatch`, whose inputs are IDs already in the database. There is no code path from a print action to an ID allocator.
2. **Module boundary.** `src/lib/print/**` and the dialog may import only `get_family_cards`. A unit test asserts that every print path calls exactly that RPC and never `generate_family_ids`, `assign_family_override`, `set_student_transport`, or `mark_student_left` — mirroring the existing "writes via RPC, never a direct UPDATE" regression test.
3. **Database.** `get_family_cards` is `STABLE` — Postgres rejects writes inside it. Generation stays admin-only; office/supervisor **cannot** generate even if a UI bug tried.
4. **UX.** Students without an ID are surfaced as *skipped*, with an admin-only "Assign a family ID →" that navigates to the setup page. The escape hatch exists but is unmistakably a different, admin-gated act.

## 10. Final flows

**User flow (reprint — the dominant case)**
```
/admin/family-ids → type "0042" or child's name → row → [Print]
  → dialog (1 card, pocket) → [Preview] → [Print 1 card] → PDF
  Same MBK-0042. No write. No generation.
```

**Print-batch flow**
```
Print one / Print selected / Print all filtered / Print by students
        └──────────────── PrintSource ────────────────┘
                            ↓
                   resolvePrintBatch(source, roster)
       drop LEFT → drop no-familyId → normalize → dedupe → expand
       to FULL sibling roster → sort by familyId
                            ↓
              PrintBatch { families, cardCount,
                duplicatesMerged, skipped* }
                            ↓
            dialog shows exact counts + skips  →  Preview
                            ↓
        get_family_cards(familyIds)   ← authoritative data, RPC
                            ↓
        FamilyCardsDocument → pdf() → blob → preview / download
```

**Data flow**
```
Google Sheet → transportImport → set_student_import_fields()   [writes govId/transport/parentPhone]
students.parentId | parentPhone → generate_family_ids()        [writes familyId — REUSES existing]
students.familyId → get_family_cards()                         [READ-ONLY → printing]
students.familyId → lookup_family()                            [READ-ONLY → gate]
```

**Student-selection edge cases**

| Case | Behaviour |
|---|---|
| No `familyId` | Listed as *skipped* with reason; admin gets "Assign →" |
| Marked LEFT | Excluded from resolution **and** from every card roster |
| Several siblings | One card, **all** siblings listed — including unselected ones |
| Two students, same family | Merged; "1 duplicate family merged" shown |
| Inconsistent family info | Row flags a mismatch; resolution stays in the admin override flow |
| No parent name | Card prints without it (never blank-fails); RPC now supplies it where it exists |
| Mixed transport | Card shows **all distinct modes** ("Bus 9 · Lug"); filter matches if **any** child matches |
| Has ID but not on latest sheet | Prints normally — the sheet is not the enrolment source of truth |

## 12. Acceptance criteria

**Family-ID stability (highest priority)**
1. A new sibling with the same `parentId` joins the **existing** family ID; Generate reports `studentsJoined`, not a new family.
2. A student with a matching `parentPhone` (no `parentId`) joins the existing family ID.
3. `mark_student_left(true)` then restore leaves `familyId` **unchanged**; no re-generation occurs.
4. A LEFT student never appears in `lookup_family`, on a card, or in a family row — while retaining their ID.
5. Re-running Generate any number of times changes zero existing `familyId` values.
6. Re-importing the transport sheet changes zero existing `familyId` values.
7. Only one `generate_family_ids` overload exists; the no-argument client call resolves unambiguously to the transport-filter body.

**Printing**
8. **One family** → exactly 1 card, front + back, correctly duplex-aligned.
9. **N selected** → exactly N cards; count shown on the button *and* in the dialog.
10. **Print all filtered** → every family matching current filters, count stated.
11. **By students**: A(0042), B(0042), C(0071) → exactly **2** cards, with "3 students → 2 cards · 1 duplicate merged".
12. Every card lists **all** current siblings, including unselected ones.
13. Reprinting reuses the same `MBK-####` and performs no write.
14. Search matches `0042`, `42`, `MBK-0042`, student name, parent name, phone.
15. Select-all-filtered / clear selection behave exactly; selection is keyed by `familyId` and survives filter and sort changes.

**Correctness and safety**
16. Admin, supervisor and office printing the same family produce **identical** cards (same siblings, parent name, phone).
17. The phone on the card equals the phone `lookup_family` shows at the gate.
18. Mixed-transport families show all distinct modes and match a transport filter if **any** child matches.
19. Duplex regression test locks the measured geometry for 1–9 cards (guards `justifyContent: 'center'`).
20. Students without a `familyId` are listed as skipped, never silently dropped.

**Separation**
21. No print path calls `generate_family_ids`, `assign_family_override`, `set_student_transport`, or `mark_student_left` — asserted by test.
22. `get_family_cards` is `STABLE` and role-gated to admin/supervisor/office; `PUBLIC` execute revoked.

**Permissions**
23. Supervisor and office can browse and print; `/admin/family-ids/setup` is admin-only and enforced by `canAccessRoute()`, the App switch, **and** SQL.
24. Teacher and parent cannot reach either route; a parent can still print only their own family.

**States and performance**
25. Empty / loading / error / partial states for the table, the dialog, and PDF generation; a render failure names the family and preserves the selection.
26. 143 families render in < 10 s in-browser with a spinner and a disabled button; the table stays responsive at 200+ families and usable at 375 px.
27. `npm run typecheck` clean; `npx vitest --run` **260/260 + new tests**; `vite build` succeeds.

# FINAL RECOMMENDATION

**Architecture C (hybrid), with Review B's route split:**
`/admin/family-ids` — searchable, filterable, selectable family table where **every** print path (row · selected · all · by-students) opens **one shared Print Batch dialog**.
`/admin/family-ids/setup` — admin-only import + generation.
Printing is **family-based**; student selection is an input mode resolved by a single pure `resolvePrintBatch()`. Card data is read through one `get_family_cards()` RPC. **No `families` table. No print history in Phase 1.**

## WHY THIS IS THE BEST

* Optimises the **actual dominant job** — find a family and reprint one card in ~3 clicks — while making the once-a-year 143-card run safe with one confirming step that states the exact count.
* **One resolution path** means duplicate-family collapsing, the card count, skip reporting, and preview exist in exactly one place and cannot drift.
* The route split gives office staff a screen containing only what they may do, and stops a 936-line component from growing further.
* It fixes the **real** defects (family splitting, ID destruction, incomplete cards) and **declines** the three phantom ones the prior reviews asserted — measurement over inference.
* It adds **one** database function in Phase 1 and no new tables, honouring "avoid unnecessary database complexity."
